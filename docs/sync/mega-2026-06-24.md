## 1. 仓库关系与模块映射

`monoengine` 不是 `mega` 的镜像，而是把 mega **部分** crate 扁平化进单 crate `src/`，并在此基础上做了大量重构（config/vault/mail/notification/contract/orbit，见 `docs/refactoring/`）。它**刻意不包含** orion 构建机群、clients、Web UI（moon）、buck2/docker/CI 工具链。

| mega crate / 路径 | monoengine 对应 | 说明 |
|---|---|---|
| `jupiter/`（storage/service/migration/redis） | `src/jupiter/` | 存储层，已移植并重构 |
| `jupiter/callisto/` | `src/callisto/` | sea-orm 实体（mono 反而更多：81 vs 71） |
| `ceres/` | `src/ceres/` | git pack 协议 / build_trigger / code_edit |
| `common/` | `src/common/` | errors/utils；config 已提升为一级 `src/config/` |
| `saturn/` | `src/saturn/` + `src/contract/policy/` | cedar 策略 |
| `vault/`（mega 集成层，1188 行） | `src/contract/vault/` | 产品集成层 |
| *(`libvault-core` 发布版 crate)* | `src/vault/`（**vendored**，23k 行） | monoengine 内联了 RustyVault，**不跟随 mega** |
| `context/` | `src/context/` | AppContext |
| `api-model/` | `src/contract/api/`（api_model） | DTO |
| `mono/`（服务 bin crate） | `src/server/`、`src/api/`、`src/commands/`、`src/cli.rs` | 服务/CLI |
| `io-orbit/` | `orbit-api` 依赖 + 外部 `../orbit` | 对象存储已外置（见 orbit.md） |
| `orion*` / `clients` / `moon` / `docker` / `scripts` / `.github` / `tools` | **无** | 构建机群 / 前端 / CI，超出移植范围 |

> monoengine 独有（mega 无对应顶层 crate）：`config`（一级化）、`mail`、扩充后的 `notification`、`bellatrix`、`chat`、`email`。

### 3.3 重点：git-internal 0.7.4 → 0.7.6（核验细节）

子代理下载并 diff 了三个发布版的完整源码：**仅 3 个文件变化**（`internal/object/tag.rs`、`internal/pack/cache.rs`、`internal/pack/decode.rs`），`lib.rs` 导出与 `[dependencies]` 均未变。monoengine 在 ~33 个文件 / 63 处引用 git-internal（Hash/SHA1、object 解码、Tree/Commit/Blob、errors）。

- **唯一签名变化**：`Caches::remove_tmp_dir(&self) -> ()` 改为 `-> io::Result<()>`。**monoengine 未调用此方法**，无影响。
- **`decode.rs`**：内部硬化，把若干 `unwrap()` 改为返回 `GitError`，无 public 签名变化，纯健壮性提升。
- **⚠️ `Tag::new` 行为（非签名）变化**：现在 `tag.id` = 序列化 `to_data()` 字节的规范 git 对象哈希（与 `Commit::new` 一致）；**0.7.4 之前算出的 OID 与存储/打包字节不符（是 git-不正确的）**。这是一个正确性修复，但**会改变带注释 tag（annotated tag）的 OID 取值**。
  - **行动项**：(a) 升级后重测「带注释 tag 的 create/fetch/push/repack」流程及任何断言 tag OID 的快照/golden 测试；(b) 注意 DB 中既有 tag 行可能携带旧（错误）OID，若有消费方与新哈希比对需回填/对账。

## 5. 唯一需要移植的源码变更：#2111（删除 build_events.log 死列）

`build_events` 表的 `log` 列从未被写入（日志实际由 `log_output_file` 指向 artifact 存储），mega将其作为干净的 schema 清理删除。monoengine **承载 build_events 表**（`m20260208_012349_change_build_events.rs:43` 创建了该 `Log` 列），故此变更**适用且当前缺失**。

建议改动（仅共享部分，跳过所有 orion-server/moon/.github 文件）：

1. `src/callisto/build_events.rs`：删除实体中的 `pub log: Option<String>,`（约第 14 行）。
2. 新建 `src/jupiter/migration/m20260612_011232_drop_build_events_log.rs`：照搬mega迁移（`up`: drop `BuildEvents::Log`；`down`: 以 nullable string 重建；本地 `DeriveIden` 枚举 `BuildEvents { Table, Log }`）。
3. `src/jupiter/migration/mod.rs`：在 mod 声明块加 `mod m20260612_011232_drop_build_events_log;`，并在迁移 vec 末尾加 `Box::new(m20260612_011232_drop_build_events_log::Migration),`。注意 monoengine 的 mod.rs 已有更晚的迁移（chat/notification 直到 m20260623），新迁移按时间戳插入需保证顺序自洽。

> 风险：低。死列删除，自包含；但属 schema 变更，应在 `apply_migrations` 测试与现有 build_events 相关测试下回归。
