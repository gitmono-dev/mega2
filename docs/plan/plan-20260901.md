# Mega FastCDC 与并发可靠性同步计划（2026-09-01）

**模板版本:** `v2`（2026-07-29 起生效；本计划按 `docs/plan/plan-template.md` v2 编写）。

## 文档职责

本文解决 Mega 主线在 `bb3ef17`（PR #2178）及其前置提交中新增或强化、且当前 `monoengine` 尚未完整具备的能力：FastCDC media transport、receive-pack 状态一致性、导入索引性能、批量写入容错和多实例 ID 生成。

目标是交付一个可通过 feature gate 控制的 FastCDC 媒体传输能力，并补齐 Git receive-pack 与高并发导入路径中的安全和可靠性缺口。本文只规划任务，不宣称实现完成；每张任务卡开工前必须按 ER-02 刷新源码锚点。

### 适用范围

- `src/ceres/lfs/`、`src/api/router/lfs_router.rs`：FastCDC 分块、manifest、Media service 和 HTTP API。
- `src/orbit_api/`、`src/orbit/`：Media namespace、有界流式对象写入和 multipart 背压。
- `src/ceres/protocol/`、`src/ceres/pack/`、`src/jupiter/storage/`：receive-pack 状态机、CAS 删除和导入 filepath 批处理。
- `src/jupiter/redis/`、`src/jupiter/utils/id_generator.rs`：分布式 worker ID 选择和 Redis 租约。
- 对应单元/数据库/进程级测试、Git 协议 smoke、运行时 OpenAPI、开发文档和本计划索引。

### 非目标

- 不直接移植 Mega 的 workspace 目录结构、`MonoApiService` facade、`io-orbit` 错误类型或其它已被 monoengine 重构的架构表面；只按当前单 package 与内置 `src/orbit*` 结构适配。
- 不删除当前 `ObjectNamespace::Attachment`，也不改变现有 Git、LFS、Artifact 和 Log 对象的存储路径。
- 不新增 FastCDC 数据库 entity 或 migration；pending/finalized manifest 和 chunk 使用对象存储，标准 LFS fallback 复用既有 `lfs_objects`。
- 不移植 Mega 的 Orion、Campsite identity、Moon/Monoui、Issue/notification 和 `scripts/crates-sync` 行为；后者若未来需要，由 `DEFER-FC-03` 承接。
- 不把 FastCDC 默认切换为所有 LFS 客户端必须使用的模式；旧 LFS API 必须保持可用。
- 不在本计划中处理 FastCDC range-read、压缩编码或第三方 `fastcdc` crate 兼容层。

### 成功定义

- 开启 `fastcdc` feature 后，认证用户可通过 Media route suffix `media/v1` 完成分块 prepare、上传、finalize、查询和下载；文中 `/libra/media/v1` 表示逻辑 API 前缀，最终 URL 必须由 FC-07 按当前 `routers()`/server mount 组合并记录；关闭 feature 时现有 LFS 行为不变。
- FastCDC manifest、chunk hash、对象 scope 和 fallback 具有固定且可跨 Mega/Libra 客户端复现的协议语义。
- 同一用户/仓库可断点续传与复用 chunk，不同用户或仓库不能通过 hash 交叉读取媒体数据。
- finalize 能验证全部 chunk、整对象 SHA-256 和冻结的 chunk 边界；失败时不发布不完整的标准 LFS 对象或 finalized manifest。
- receive-pack 的无 pack、tag、删除、混合命令和并发删除场景均返回明确状态，不产生错误 ref 或 panic。
- 大型导入的 filepath 更新使用批量写入；数据库序列化冲突有界重试；多实例 Snowflake worker 不默认共享固定 worker ID。
- 所有非延后任务完成后满足 `Lifecycle=done`、`Acceptance=complete`，Claude Code Review 最终给出 `PASS`，并通过计划完成门。

## 已决议设计决策

### ADR-FC-01: 按 monoengine 当前边界适配，不回流 Mega workspace 架构

- **Status:** Accepted
- **Context:** Mega 是多 crate workspace，当前 monoengine 是单 package，`io-orbit` 已内联到 `src/orbit_api/` 与 `src/orbit/`，LFS route 也不是 Mega 的 `MonoApiService` 结构。
- **Decision:** FastCDC 代码落在 `src/ceres/lfs/media/`，HTTP adapter 落在当前 `src/api/router/`，对象存储扩展当前 `MegaObjectStorage`/`ObjectStoreAdapter`，服务通过当前 `Storage`/`LfsService` 注入。保留 `OrbitResult`、`IoOrbitError` 和 `ObjectNamespace::Attachment`。
- **Alternatives considered:** 直接复制 Mega crate 文件——会引入失效路径和错误类型；重写整个 service facade——与本计划单一行为轴不符。
- **Consequences:** 需要逐文件重建测试和 import 路径，但不会破坏 monoengine 已完成的 orbit、vault 和单 package 收敛。
- **Revisit when:** monoengine 再次拆分 workspace 或建立独立 LFS service facade。

### ADR-FC-02: FastCDC wire contract 固定为内置 `fastcdc-v1`

- **Status:** Accepted
- **Context:** Libra 需要与 Mega 使用完全一致的 chunk boundary 和 manifest ID；第三方 crate 的版本或 Gear table 变化会造成不可互操作。
- **Decision:** 使用 Mega `bb3ef17` 中相同的 `splitmix64(seed)` Gear table 生成规则、mask、min/avg/max 和 SHA-256 规则；manifest version 为 1，chunk compression 固定 `none`，hash 使用 64 位小写 hex。
- **Alternatives considered:** 引入第三方 `fastcdc` crate——算法参数和输出可能漂移；使用标准 LFS 整对象——不能提供 chunk 去重和断点续传。
- **Consequences:** 这是公开存储/协议格式，一旦启用需长期兼容；变更必须新建 algorithm/version，不允许静默修改 v1。
- **Revisit when:** 需要压缩 chunk、range read 或新算法协商时。

### ADR-FC-03: finalized media 必须发布标准 LFS fallback

- **Status:** Accepted
- **Context:** 旧版 Git LFS 客户端不了解 Media API；只发布 chunk manifest 会导致旧客户端无法使用媒体对象。
- **Decision:** finalize 验证通过后，以标准 LFS OID/size 写入 `ObjectNamespace::Lfs` 和 `lfs_objects`，然后才发布 finalized manifest。重复 finalize 使用幂等 metadata insert。
- **Alternatives considered:** 只保存 Media chunk——破坏旧客户端兼容；先发布 fallback 再验证 manifest——会留下不可验证对象。
- **Consequences:** finalize 是跨对象存储和 DB 的多阶段流程，采用 forward-only 兼容策略；失败重试不得重复损坏发布。
- **Revisit when:** 标准 LFS fallback 已经过完整 deprecation 窗口且所有客户端支持 Media。

### ADR-FC-04: Snowflake 位宽变更必须禁止旧新 writer 混跑

- **Status:** Accepted
- **Context:** 当前 `idgenerator` 实际使用 worker bits=6、sequence bits=8，时间戳左移量由两者之和得到 14；Mega 目标使用 worker bits=8、sequence bits=8，派生左移量为 16。两种布局在滚动发布重叠期间不能假设 ID 空间天然兼容。
- **Decision:** FC-13 固定总低位预算为 `8 + 8 = 16 <= 22`，并显式验证 `idgenerator 2.0.0` 的约束；时间戳左移量由 `worker bits + sequence bits` 派生为 16。部署必须在所有旧 writer 停止后启用新布局；若发布平台不能保证该窗口，则保留旧的 6+8 布局，仅以前滚方式增加动态 worker 选择，不得让两种位宽同时生成 ID。开工时扫描仓库是否存在按位解析既有 ID 的消费者，发现则先阻塞 FC-13。
- **Alternatives considered:** 直接把 6 位改成 8 位并允许滚动发布——可能发生跨布局碰撞；保留 6 位永久不支持超过 64 worker——牺牲多副本容量但可作为无法协调重启时的安全 fallback。
- **Consequences:** FC-13 是 minor 级别的运行时兼容变更，已生成 ID 不重编码、不回收；需要发布前维护窗口或明确采用旧布局 fallback。
- **Revisit when:** ID generator 支持显式 version/epoch 或部署平台提供可验证的全量 writer fence。

### 故障恢复矩阵

| 故障点 | 可接受残留 | 恢复动作 | 禁止结果 |
|---|---|---|---|
| manifest JSON/size/hash invalid | 无对象写入或未完成 pending | 返回 400，丢弃请求 | panic、部分 finalize |
| chunk upload 中途失败 | 未 finalized 的 scoped pending/chunk | abort/TTL 回收，允许重试 | chunk 写入其它 scope |
| finalize chunk/hash/boundary 失败 | 临时文件和未 finalized 对象 | 清理临时文件，不发布 fallback/manifest | 旧客户端读到不完整 LFS 对象 |
| fallback 已发布但 manifest publish 失败 | 完整标准 LFS fallback | 通过幂等重试补 manifest | 删除可用 fallback 或报告成功但不可读 |
| receive-pack status validation 失败 | command status only | 返回 `ng`，不写错误 ref | 先持久化再报告失败 |
| CAS delete old id mismatch | 新 ref 保留 | 返回 conflict/status，客户端重试 | 删除后来写入的 ref |
| DB batch transient error | 未提交 batch | ≤5 次退避重试，超限 blocked | 吞掉真实 constraint/table error |
| Redis worker lease 丢失 | 已生成 ID 不回收 | 停止续租并以前滚/显式 ID 重新启动 | 重用已发布 worker/sequence 空间 |
