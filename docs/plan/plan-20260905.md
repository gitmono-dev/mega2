# Trunk 直推形态（storage-only）与 Monorepo 写入序列化计划（2026-09-05）

**模板版本:** `v2`（2026-07-29 起生效；本计划整份符合 `docs/plan/plan-template.md` v2）。

## 文档职责

本文解决「monorepo 根树写入无序列化（并发写入互相覆盖、路径 ref 与根树视图分叉）」与「不接入用户系统、不使用 Issue 与 Change List 的 storage-only 部署形态下，Git 推送如何直接落入 `main`」两个问题，目标是交付：**`MonoWriteQueue` 全局写入序列化（顺序 + 事务级 advisory lock + 根 ref CAS tripwire）、后代 ref 续接与墓碑、合成 commit 的真实归属与 provenance、`push_policy = "trunk"` 直推形态、无用户系统的静态 token 推送认证**。

设计事实源是 `docs/refactoring/trunk-push.md`（2026-09-05 修订 66，经 Codex/Claude 双评审 PASS——Codex 第 59 轮、Claude 第 3 轮；事实校准 17 条、ADR-TP-01..20 含 15a、不变式 I1–I6 含 I2a、阶段 1 交付物 10 项、修订记录 66 条）。本计划不复制其设计论证，只把已决议设计落成可执行任务卡；实现时若需偏离 ADR，必须先修改 trunk-push.md 与本计划并说明原因。

**与事实源的阶段对齐（2026-09-05 修订 2）**：trunk-push.md 在双评审中把基础静态 token 认证自阶段 5 前移至**阶段 4 的 4.2a**（`push_policy=trunk` 强制显式 `push_auth`），阶段 5 收窄为「多 token 运维与认证强化」且未给出可执行规范——本计划据此把 TP-19/TP-20 移入 Phase 4，阶段 5 的多 token 运维登记为 **DEFER-TP-05**（重启条件 = trunk-push.md 阶段 5 补齐规范）。另据同批评审修订：阶段 1 不可独立上线生产（其删除式后代处理违反 I1，生产部署以阶段 2/TP-14 为前置）；B0 不做任何拒绝性 NFF 判定（遥测）；`pending_action` 仅保留 `requeue_conflict`（根绕过判定由 B2.5 落库的 `expected_*` 基线 + reaper 通用 I3 修复承担）；trunk 形态 LFS 不可用。

本文只规划任务，不宣称实现完成。落地时每个任务都必须先刷新源码锚点（GC-01），再按任务卡验收。

### 非目标

- **不改 review 形态的既有语义**：阶段 1–3 的队列化与缺陷修复不得改变 CL 创建/检查/合并的判定、门控与拒绝面；既有测试用例期望值不得修改。两类登记在案的显式豁免：后代 ref 续接（缺陷修复本身）与 merge 的队列生命周期变化（背压、`wait_timeout`、异步转同步）——见 trunk-push.md 硬约束 8。
- **不引入用户系统 / Issue / Change List**：trunk 形态的认证只交付 git-over-HTTP 静态 token；SSH receive-pack 在 storage-only 形态下不暴露（TP-20）。
- **不做多分支单推送、merge commit 入链、根路径 clone**：沿用 ADR-MC-04 / MC-03 的既有拒绝面；根路径推送不作为该形态假设。
- **不做 Redis 队列、不做乐观 CAS 并发模型**：ADR-TP-01/02 已否决。
- **不承诺逐 commit GPG 签名验证**：ADR-TP-15a，N=1 的签名保留是零改写副产物、非可依赖保证。
- **阶段 6 四项优化（group commit / LISTEN-NOTIFY / 实时进度 / 物化 TTL）不进入本计划执行**：登记为 DEFER-TP-01..04，无实测压力证据不启动。
- **阶段 5 的多 token 运维与强化不进入本计划执行**：登记为 DEFER-TP-05（trunk-push.md 阶段 5 收窄后未给出可执行规范；基础认证已随 4.2a 进阶段 4/TP-19）。
- **trunk 形态 LFS 不可用**：LFS 路由经 `UserStorage` 认证（`lfs_router.rs:205-213/235-250`），静态 token 模型不覆盖 LFS 批/锁授权——trunk 形态关闭 LFS 写路由并在部署文档声明（TP-18）；token-aware LFS 授权为独立议题。

### 成功定义

- 全部根树与路径 ref 写入者（trunk 推送、CL merge、ImportRepo attach、两条惰性物化路径）要么经 `MonoWriteQueue` 串行、要么被 ADR-TP-20 机制显式覆盖；根 ref CAS 断言恒不失败（不变式 I5）。
- 并发写入不再互相覆盖：根树在任一提交边界等于所有路径子树的一致快照（不变式 I3）；已物化路径历史只增不改（I1）；每次推送在每个受影响的层恰好前进一个 commit（I2a）。
- `push_policy = "trunk"` 下：N = 1 推送客户端 commit 原样落地（hash/作者/时间/message 逐字不变），N > 1 自动 squash 为一个 commit 且 tree 保真（I2），squash message 完整枚举全部 N 条不截断（I4）；trunk 与 `cedar.enforcement != "off"` 互斥于启动期 fail-closed 拒绝。
- 无用户系统部署可经静态 token 推送（`push_auth = "token"`，组件边界路径授权；`push_auth = "none"` 需显式配置；`push_auth ∈ {token,none}` 强制 `push_policy = "trunk"`，反向 `trunk` 强制显式 `push_auth`——4.2a 随阶段 4 交付）。trunk 形态 LFS 不可用（TP-18）。
- 全部 23 张任务卡（TP-01..TP-23）`Lifecycle=done` 且 `Acceptance=complete`；三门全绿；外部双评审（Codex/Claude）对本计划 PASS；`docs/monorepo.md` 反向声明与部署文档同步完成。

## 全局工程约束

本节不重述 `docs/plan/plan-template.md` v2 的 GC-01..GC-12 全文，**全部继承**；以下为本计划特有补充：

- **GC-TP-01 队列纪律（I5 前提）:** 任何改写根树或 `refs/heads/main` 行的代码必须经 `MonoWriteQueue`、在审计清单中登记为队列外并被 ADR-TP-20 覆盖、**或属于服务接流前完成并持专属锁的 bootstrap**（`initialize_monorepo`，`mono_service.rs:103-125`——trunk-push.md 硬约束 2 的第三类，I5 三分法）。不得在 B3 事务之外新增根 ref 写入点；新增写入者必须同步 trunk-push.md 硬约束 2 的清单与本计划。
- **GC-TP-02 B3 单事务:** 轮次的 ref/commit/tree/CL 状态写入必须在同一 `&DatabaseTransaction` 内；禁止在 B3 内使用自建连接的原语（`batch_update_by_path_concurrent` 原形、自建连接的 `remove_none_cl_refs` 等）。merge/rebase 的 CL 行更新一律携带单调 revision 全量 CAS（GAP-12，双向串行化）；CL 创建/检查等其他状态写不受影响（trunk-push.md 1.11/1.9）。
- **GC-TP-03 review 形态可观察行为不变（硬约束 8）:** 阶段 1–3 的任务不得改变 CL 创建/检查/合并的判定、门控与拒绝面；既有测试用例期望值不得修改。**三类登记在案的豁免**（trunk-push.md 登记在案，仅限其验收标准所列行为变化）：①后代续接缺陷修复；②merge 队列生命周期变化（背压/`wait_timeout`/异步转同步）；③**文件路径索引的形态隔离规则**（队列轮次打水位后，review 推送的索引仅 `IS NULL` 行生效——trunk-push.md ADR-TP-11 登记为有意设计，索引不在写入判定链上）。
- **GC-TP-04 失败可见性:** 禁止沿袭「空 refs / capabilities-only / 静默跳过」的失败模式（`smart.rs:76-88` 把空 refs 编码为 capabilities-only、`mono_storage.rs` 静默跳过缺失行）；物化放弃、被拒轮次、CAS 失败都必须产生可诊断报错或显式终态。B0 的乐观 NFF 预检**只作遥测不拒绝**——拒绝权威唯一归属 B3（无锁的 B0 拒绝会在陈旧行修复前放逐客户端）。
- **GC-TP-05 CAS 是 tripwire 不是完备性证明:** 根 ref CAS 恒成功不等于不存在未登记写入者；完备性第一依据是写入者审计（Phase 0 登记、trunk-push.md 硬约束 2 清单），CAS 与巡检是兜底。
