# Trunk 直推形态（storage-only）与 Monorepo 写入序列化计划（2026-09-05）

**模板版本:** `v2`（2026-07-29 起生效；本计划整份符合 `docs/plan/plan-template.md` v2）。

## 文档职责

本文解决「monorepo 根树写入无序列化（并发写入互相覆盖、路径 ref 与根树视图分叉）」与「不接入用户系统、不使用 Issue 与 Change List 的 storage-only 部署形态下，Git 推送如何直接落入 `main`」两个问题，目标是交付：**`MonoWriteQueue` 全局写入序列化（顺序 + 事务级 advisory lock + 根 ref CAS tripwire）、后代 ref 续接与墓碑、合成 commit 的真实归属与 provenance、`push_policy = "trunk"` 直推形态、无用户系统的静态 token 推送认证**。

设计事实源是 `docs/refactoring/trunk-push.md`（1631 行，2026-09-04 事实校准，ADR-TP-01..20 含 15a，不变式 I1–I6 含 I2a）。本计划不复制其设计论证，只把已决议设计落成可执行任务卡；实现时若需偏离 ADR，必须先修改 trunk-push.md 与本计划并说明原因。

本文只规划任务，不宣称实现完成。落地时每个任务都必须先刷新源码锚点（GC-01），再按任务卡验收。

### 适用范围

- 队列基础设施：新增 `push_queue` / `queue_control` 实体与迁移、`MonoWriteQueue` storage/service/router 四层（泛化自 `merge_queue`）、B0–B4 算法、reaper、控制面。
- 根树写入路径：`src/ceres/api_service/mono_api_service.rs`（`merge_cl_unchecked` / `apply_update_result` / `process_ref_updates`）、`src/ceres/pack/import_repo.rs`（attach）、`src/ceres/pack/monorepo.rs`（`finalize_receive_pack` / `refs_with_head_hash` / `traverses_tree_and_update_filepath`）、`src/jupiter/storage/mono_storage.rs`。
- 一致性机制：`mega_ref_tombstones` 墓碑表、`blob_paths` 出现对索引表、B3 树哈希断言、物化插入校验、对账与周期巡检。
- 配置与认证：`[monorepo].push_policy`、`[monorepo].max_push_commits`、`[git].push_auth` / `[[git.push_tokens]]`、`src/server/http_server.rs` 启动门槛、`src/contract/git_protocol/` 认证挂点。
- 测试与文档：`tests/integration_git_cli.rs`、`scripts/git_protocol_smoke.sh` 本地等价、`docs/refactoring/trunk-push.md` 的同步、`docs/monorepo.md` 反向声明、部署文档。

### 非目标

- **不改 review 形态的既有语义**：阶段 1–3 的队列化与缺陷修复不得改变 CL 创建/检查/合并的判定、门控与拒绝面；既有测试用例期望值不得修改。两类登记在案的显式豁免：后代 ref 续接（缺陷修复本身）与 merge 的队列生命周期变化（背压、`wait_timeout`、异步转同步）——见 trunk-push.md 硬约束 8。
- **不引入用户系统 / Issue / Change List**：trunk 形态的认证只交付 git-over-HTTP 静态 token；SSH receive-pack 在 storage-only 形态下不暴露（TP-20）。
- **不做多分支单推送、merge commit 入链、根路径 clone**：沿用 ADR-MC-04 / MC-03 的既有拒绝面；根路径推送不作为该形态假设。
- **不做 Redis 队列、不做乐观 CAS 并发模型**：ADR-TP-01/02 已否决。
- **不承诺逐 commit GPG 签名验证**：ADR-TP-15a，N=1 的签名保留是零改写副产物、非可依赖保证。
- **阶段 6 四项优化（group commit / LISTEN-NOTIFY / 实时进度 / 物化 TTL）不进入本计划执行**：登记为 DEFER-TP-01..04，无实测压力证据不启动。

### 成功定义

- 全部根树与路径 ref 写入者（trunk 推送、CL merge、ImportRepo attach、两条惰性物化路径）要么经 `MonoWriteQueue` 串行、要么被 ADR-TP-20 机制显式覆盖；根 ref CAS 断言恒不失败（不变式 I5）。
- 并发写入不再互相覆盖：根树在任一提交边界等于所有路径子树的一致快照（不变式 I3）；已物化路径历史只增不改（I1）；每次推送在每个受影响的层恰好前进一个 commit（I2a）。
- `push_policy = "trunk"` 下：N = 1 推送客户端 commit 原样落地（hash/作者/时间/message 逐字不变），N > 1 自动 squash 为一个 commit 且 tree 保真（I2），squash message 完整枚举全部 N 条不截断（I4）；trunk 与 `cedar.enforcement != "off"` 互斥于启动期 fail-closed 拒绝。
- 无用户系统部署可经静态 token 推送（`push_auth = "token"`，组件边界路径授权；`push_auth = "none"` 需显式配置）。
- 全部 21 张任务卡 `Lifecycle=done` 且 `Acceptance=complete`；三门全绿；评审 PASS；`docs/monorepo.md` 反向声明与部署文档同步完成。

| ADR | 决策摘要 | 承接卡 |
|---|---|---|

## 全局工程约束

本节不重述 `docs/plan/plan-template.md` v2 的 GC-01..GC-12 全文，**全部继承**；以下为本计划特有补充：

- **GC-TP-01 队列纪律（I5 前提）:** 任何改写根树或 `refs/heads/main` 行的代码必须经 `MonoWriteQueue`（或在审计清单中登记为队列外并被 ADR-TP-20 覆盖）。不得在 B3 事务之外新增根 ref 写入点；新增写入者必须同步 trunk-push.md 硬约束 2 的清单与本计划。
- **GC-TP-02 B3 单事务:** 轮次的 ref/commit/tree/CL 状态写入必须在同一 `&DatabaseTransaction` 内；禁止在 B3 内使用自建连接的原语（`batch_update_by_path_concurrent` 原形、自建连接的 `remove_none_cl_refs` 等）。
- **GC-TP-03 review 形态可观察行为不变（硬约束 8）:** 阶段 1–3 的任务不得改变 CL 创建/检查/合并的判定、门控与拒绝面；既有测试用例期望值不得修改。两类豁免（后代续接缺陷修复、merge 队列生命周期变化）在 trunk-push.md 登记在案，仅限其验收标准所列行为变化。
- **GC-TP-04 失败可见性:** 禁止沿袭「空 refs / capabilities-only / 静默跳过」的失败模式（`smart.rs:76-88` 把空 refs 编码为 capabilities-only、`mono_storage.rs` 静默跳过缺失行）；物化放弃、被拒轮次、CAS 失败都必须产生可诊断报错或显式终态。
- **GC-TP-05 CAS 是 tripwire 不是完备性证明:** 根 ref CAS 恒成功不等于不存在未登记写入者；完备性第一依据是写入者审计（Phase 0 登记、trunk-push.md 硬约束 2 清单），CAS 与巡检是兜底。

## 性能与容量摘要

| 操作 | 单次成本 | 累积成本 | 预算/上限 | 验证 |
|---|---|---|---|---|

| 物化插入 | 短锁事务（毫秒级） | 冷读路径每路径一次 | 重试 K=2 有界 | TP-10 |
| 对账/巡检 | 全量比对 O(已物化行数)，分批持锁 | 周期任务 | 频率/告警阈值可配 | TP-11 |
