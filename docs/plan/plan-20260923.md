## 文档职责

本文解决五个首次使用问题：新子路径无法用普通 Git/Libra 流程开通，且错误文案不可操作（#25 / #29）；ImportRepo 第二次推送被拒，与文档矛盾（#26）；失败或废弃的 ImportRepo 叶子无法清理（#27）；签名 commit 推到子路径后 Mega2 合成的祖先层 commit 主题变成 `gpgsig -----BEGIN PGP SIGNATURE-----`（#28）。目标是：稳定、可操作的路径策略错误码；幂等的路径开通操作（HTTP + CLI）；可增量更新、按 Git 语义做 ref CAS 的 ImportRepo；有鉴权、可审计、可续做的 ImportRepo 清理；不泄漏签名头、帧格式正确的服务端合成 commit。

本文只规划任务，不宣称实现完成。落地时每个任务都必须先刷新源码锚点，再按任务卡验收。

- 用 Git push 创建新的顶层根目录；运行时增删根目录（`root_dirs` 变更仍需重启）。
- 改变单 trunk / 客户端 tag 策略；在普通 Monorepo 路径开放多分支或客户端 tag。
- ImportRepo 目录内的文件级删移（`delete-entry` / `move-entry` 对 ImportRepo 内部路径的拒绝保持不变）；未鉴权的破坏性端点。
- Git 命名空间对象存储 GC（`DEFER-FU-01`）；`atomic` 推送能力（`DEFER-FU-05`）。
- 改动 `../libra` 仓（`DEP-FU-03`）；review 形态的新增表面（`DEFER-FU-02`）。
- 重写历史 commit（`DEFER-FU-07` 永久非目标）。
- 关闭或评论 GitHub issue（维护者动作）。

### 成功定义

- 无父首推到根外路径返回 `MONO_PATH_NOT_ALLOWED`（列出允许的根），到合法根下未开通路径返回 `MONO_PATH_UNINITIALIZED`（点名开通动作）；重试同一 commit 得到同一码；真实 non-fast-forward 保持原文与对齐提示。
- `mega2 path provision --server <url> <path>` 或 `POST /api/v1/path/provision` 在全新栈上一次开通、重试报告已存在；之后 Git clone → commit → 两次增量 push 全部成功，无需手写 HTTP。
- ImportRepo 第二次 fast-forward push、后续新分支与 tag 推送成功；陈旧 ref 更新被拒；失败文案为稳定码。
- 有鉴权的 `POST /api/v1/import-repo/remove` 删除一个完整 ImportRepo 叶子：之后 404，重试稳定返回 `absent`，留下事务内审计行；不能删除 import 根、不能越出命名空间、不能经前缀匹配误删兄弟仓库。
- 签名 commit 推到任意子路径后，Mega2 合成的祖先/后代/物化 commit 主题等于原 commit 主题；合成 commit 通过 `git fsck --strict`；`git -c transfer.fsckObjects=true clone` 成功。
- 非延后卡 `Lifecycle=done` 且 `Acceptance=complete`；每张卡 Codex 评审最终 `VERDICT: PASS`；三门、`cargo build`、`cargo build --tests` 全绿。

### ADR-FU-01: 派生消息 = 源 commit 正文；按字节级文法剥离额外头（#28）

- **Status:** Accepted
- **Context:** git-internal 把 committer 行后的一切放进 `Commit.message`。Mega2 在 N=1 层消息、squash 主题、物化 commit、ImportRepo attach 根消息四处把它当作纯消息复用（E9–E11）。
- **Decision:**
  1. 在 `src/common/utils.rs` 提供唯一 helper `split_commit_message(message: &str) -> CommitMessageParts<'_> { headers: Vec<(&str, String)>, body: &str }`（键借用自原消息，值为拼接后的续行），文法（按字节，不 trim、不改 CRLF）：
     - `message` 以 `\n` 开头 → `headers = []`，`body = message[1..]`。
     - 否则逐行（以 `\n` 结尾）解析额外头块：行以单个空格开头 → 续行，必须有前一个头，否则整块判定为「非头块」；行为 `key SP value`，`key` 由 `[A-Za-z0-9-]` 组成且非空 → 新头；遇到空行 → 头块结束，`body` = 其后全部字节；遇到其它行或文件结束仍无空行 → 整块判定为「非头块」。
     - 「非头块」回落：`headers = []`，`body = message`（原样；覆盖历史未成帧消息，如 `create new directory demo`）。
     - 签名头 = key 为 `gpgsig` 或 `gpgsig-sha256` 的头（PGP 或 SSH armor 均由续行文法覆盖；截断/畸形 armor 仍按续行确定性解析）。正文中以 `gpgsig` 开头的行（位于空行之后）属于正文。
     - 既有 `parse_commit_msg`（`trim_start`、不识别 `gpgsig-sha256`）由新 helper 取代，零调用后删除（GC-02）。
  2. 派生 commit 只携带正文：签名头与其它额外头（`encoding`、`mergetag`、未知头）均不带入 Mega2 自己合成的 commit（helper 仍返回全部头，不丢信息）。
  3. `TrunkProvenance::from_tip` 的 `n1_message` = tip 正文；`commit_subject` 在正文上取首个非空行（去首尾空白，仅用于列表展示）。
  4. 签名路径不变：`sign_commit_preserving_identities` 以正文为 message，`embed_gpgsig` 负责头/体空行。
  5. 未签名派生 commit 经 `format_commit_msg(…, None)` 成帧：物化 commit 取完整正文 `format_commit_msg(body, None)`；ImportRepo attach 根 commit 保持既有「只取主题行」语义（原 `format_message()` 即取首个非空行，只认 PGP），主题 = `commit_body_subject(body)`，即 `format_commit_msg(commit_body_subject(body), None)`，对 PGP / SSH / `gpgsig-sha256` 一致。
  6. 被推路径 P 在 N=1 时仍是客户端 commit 逐字落地。
- **Alternatives considered:** 只修显示层（拒绝：Git 同样显示错）；把客户端签名头保留在合成 commit 头部（拒绝：必然验签失败）；改写历史 commit（拒绝：身份承载）。
- **Consequences:** 升级后新合成的层/物化 commit 字节与 id 变化；无签名 tip 的层消息不再多一个前导空行；历史对象不变（`DEFER-FU-07`）。
- **Revisit when:** git-internal 把额外头拆为结构化字段（`DEP-FU-02`）。

### ADR-FU-02: 服务端合成 commit 必须有头/体空行

- **Status:** Accepted
- **Context:** `Commit::from_tree_id(tree, parents, "create new directory …")` 生成缺头/体空行的对象（E12）。
- **Decision:** 生产路径所有未签名合成调用（`Commit::from_tree_id` / `Commit::new`，含 `mono_api_service.rs`、`mono_storage.rs` 与 `ImportApiService::save_file_edit`（`import_api_service.rs:475`））传入的消息经 `format_commit_msg(msg, None)` 成帧，恰好一次；签名路径（`embed_gpgsig`）既有帧不变。
- **Alternatives considered:** 改 git-internal（拒绝：外部 crate）；读出时修补（拒绝：对象身份已固定）。
- **Consequences:** 新 API commit id 变化；历史错帧对象不改写，严格客户端仍会拒收含其历史的路径——`docs/deploy-trunk.md` 登记已知限制（`DEFER-FU-07`）。
- **Revisit when:** 出现存量错帧对象迁移需求。

### ADR-FU-03: 路径策略与 ImportRepo 错误域、稳定码

- **Status:** Accepted
- **Context:** `docs/errors.md` 扩展规则要求新领域错误进 `src/common/errors/mod.rs` 并经 `MegaError` 包装；Git report-status 只能携带字符串。
- **Decision:**
  1. `PathPolicyError`：`NotAllowed { path, allowed_roots, import_dir }`、`Uninitialized { path }`、`Invalid { path, reason }`、`Conflict { path, component }`；码 `MONO_PATH_NOT_ALLOWED` / `MONO_PATH_UNINITIALIZED` / `MONO_PATH_INVALID` / `MONO_PATH_CONFLICT`。
  2. `ImportRepoError`：`PathOccupied`、`StaleRef`、`Removed`、`PathInvalid`、`HasChildren`、`CleanupNotFound`；码 `IMPORT_REPO_PATH_OCCUPIED` / `IMPORT_REPO_STALE_REF` / `IMPORT_REPO_REMOVED` / `IMPORT_REPO_PATH_INVALID` / `IMPORT_REPO_HAS_CHILDREN` / `IMPORT_REPO_CLEANUP_NOT_FOUND`。FU-12 一次性定义完整错误域（变体、码、`Display`、`ApiError` 映射）；**每个码在首次对用户暴露它的卡中登记 `docs/errors.md`**（发布安全）：FU-12 `IMPORT_REPO_STALE_REF`、FU-13 `IMPORT_REPO_PATH_OCCUPIED`、FU-18 `IMPORT_REPO_REMOVED` 与 `IMPORT_REPO_PATH_INVALID`、FU-20 `IMPORT_REPO_HAS_CHILDREN` 与 `IMPORT_REPO_CLEANUP_NOT_FOUND`（FU-16/FU-17 的原语无用户入口，不暴露）。
  3. 两者 `Display` = `"<CODE>: <人读消息>"`；`MegaError::PathPolicy(#[from] PathPolicyError)` 与 `MegaError::ImportRepo(#[from] ImportRepoError)` 用 `#[error("{0}")]`（无 `Other error:` 前缀）。同一文本进 Git `ng` 行与 API `err_message`。
  4. `ApiError` 映射：`NotAllowed` / `Invalid` / `PathInvalid` → 400；`CleanupNotFound` → 404；`Conflict` / `HasChildren` / `PathOccupied` / `StaleRef` → 409；`Uninitialized` / `Removed` 只出现在 Git 面（若到达 API 按 409）。
  5. `NotAllowed` 列出允许的根（`/<name>`，排序）与 ImportRepo 目录；任何消息不含配置文件路径、`base_dir`、数据库/对象存储地址或凭据。根名称已可经 `GET /api/v1/tree?path=/` 与 clone 读取；`push_auth=token` 下推送者在分类前已认证。
  6. `Uninitialized` 点名开通动作：`mega2 path provision --server <url> <path>` 与 `POST /api/v1/path/provision`，随后 clone、在其上提交、推送。
- **Alternatives considered:** 继续 `MegaError::Other` + `[code:xxx]`（拒绝：`docs/errors.md:77` 标为过渡）；只给 HTTP 加 JSON `code` 字段（拒绝：Git 面无法携带）。
- **Consequences:** 码是公开契约，改名需 minor + 文档。
- **Revisit when:** 统一的数值错误码注册表落地。

### ADR-FU-04: `root_dirs` 形状校验 + 「创建」白名单；import 目录优先

- **Status:** Accepted
- **Context:** #29 要求根外目标返回稳定策略错误；`root_dirs` 条目在 `init_trees` 中逐字作为根树项名，含 `/`、重复、`.`/`..`、空串的条目今日生成非法根树；默认配置同时把 `third-party` 列入 `root_dirs` 并设 `import_dir="/third-party"`。
- **Decision:**
  1. 配置校验（`config validate` 与服务启动同一路径）：`root_dirs` 每项非空、不含 `/` 或 `\`、不等于 `.` 或 `..`、不含 NUL、互不重复、无首尾空白（环境变量列表解析不 trim），且不等于 `init_trees` 自带的根条目名（`converter.rs::INIT_ROOT_RESERVED_NAMES`：`.mega_cedar.json`、`.cedar`、`.buckroot`、`.buckconfig`，否则根树重复条目）或 `.git`（不区分大小写）；`import_dir` 必须是规范绝对路径（`canonicalize_mono_ref_path(import_dir) == import_dir`）、≠ `/`、不含 NUL 与 `\`（`canonicalize_mono_ref_path` 本身接受 NUL，`utils.rs:165`，故单独校验），且其**首组件必须属于 `root_dirs`**（`init_trees` 只预建 `root_dirs`，`converter.rs:428-443`；否则首次 ImportRepo attach 会经 `search_and_create_tree` 新建顶层树，违反「不由 Git push 创建新顶层根」）。违反即校验失败并点名字段（无 secret）。`config/config.toml` 与两份 storage-only 样例配置的注释同步写明上述约束。
  2. 分类函数 `classify_creation_path(config, canonical_path)`（唯一实现，开通 API、产品写与 receive-pack 共用）输入必须已是规范路径：import 目录（组件级 `starts_with(import_dir)`）→ `NotAllowed`（附「ImportRepo 由推送创建」提示，**import 优先**，即使 `root_dirs` 含同名项）；`/` → `Invalid`；首段 ∉ `root_dirs` → `NotAllowed`；否则 `Allowed`。规范化分两种入口：**客户端 JSON 输入**（开通 API；清理 API 与运维 CLI 见 ADR-FU-10）先显式拒绝 NUL 与 `\`，再要求原始输入满足 `input == canonicalize_mono_ref_path(input)`（重复斜杠、尾斜杠、`.`/`..` 段、相对路径均判 `Invalid`；`canonicalize_mono_ref_path` 会静默规范化别名且接受 NUL，`utils.rs:160-190`）；**Git 协议 URL 路径**沿用 TP-08 的「先规范化再使用」（`protocol/mod.rs:236-262`；Git/Libra 客户端会发送带尾斜杠的远端 URL，不得因此拒绝），规范化失败或含 NUL 时拒绝。
  3. 分类只作用于**创建**动作：开通 API；trunk 下 `old_id=ZERO` 且 P 在当前根树中不可解析的推送。已可解析的路径不重新校验。
- **Alternatives considered:** 所有推送都校验首段（拒绝：会拒绝既有非 `root_dirs` 顶层目录，如 `.cedar`）；只改文案（拒绝：#29 AC1 需要稳定策略面）。
  4. 分类同样作用于**产品写**：`resolve_trunk_land_path` 找不到非根 tip 时先分类写路径，且 import 命名空间守卫无条件先行（ADR-FU-06），使 Git 与 API 对根外路径与 import 目录返回同一码。API 面三类情形的对应：「根外」→ 同一 `MONO_PATH_NOT_ALLOWED`；「合法根下未开通」→ 不是错误（产品写与开通 API 本身就是开通动作）；「真实 NFF」→ 不适用：产品写不携带客户端基线 commit，冲突由 MonoWriteQueue CAS 重排内部解决（`DEFER-FU-08` 登记理由）。
  5. B3 push 的真创建分支（`path_row` 缺失且 P 在根树不可解析）在锁内再调用一次分类（纵深防御）；`path_row` 缺失且 `old_id≠ZERO` 已由 B3 以 `cannot update missing path` 拒绝（`push_queue_service.rs:1791-1799`），因此创建只可能来自 `old_id=ZERO`。
- **Consequences:** 关闭未文档化的「fork 型创建新顶层」——FU-10 `minor`；非法 `root_dirs` 配置从「生成坏根树」变为「启动前失败」。运维新增根：改 `root_dirs` + 重启，再经 `git push` 创建该根（开通 API 不能在 `/` 落地，`DEFER-FU-14`）。
- **Revisit when:** 需要运行时增删根目录。

### ADR-FU-05: 开通操作 = 幂等 HTTP API + 薄 CLI；按最高新建组件授权

- **Status:** Accepted
- **Context:** #25 要求受支持、可发现、幂等的开通，旅程不需手写 HTTP；保留「无父提交不得静默成为任意子树」。
- **Decision:**
  1. `POST /api/v1/path/provision`，请求 `{ "path": "/project/workbuddy/demo" }`，只挂 storage-only 写路由。`mkdir -p` 语义：先 `classify_creation_path`；任一已存在组件不是目录 → `MONO_PATH_CONFLICT`；整条路径已是目录 → `200 { path, created: false, commit_id: null }`，零写；否则一次 commit 补齐全部缺失层（叶子带 `.gitkeep`），经 `commit_tree_update` → MonoWriteQueue → `200 { path, created: true, commit_id }`。建树由开通专用、绑定单一根树快照的构建器完成（FU-07 R1 起不复用 create-entry 的子串式缺失层推导）：落地前以同一快照重算最高新建组件并与已鉴权的计划比对，落点 tip 的 tree 与快照不一致时重来（见本计划变更记录 FU-07 R1）。
  2. 授权：所需范围 = 本次请求将新建的**最高**路径（第一个缺失组件）；无需新建时 = 目标路径。以该路径调用 `authorize_trunk_api_write`。每次 prepare 重新计算（落地 CAS 失败重 prepare 时重新授权），防止 TOCTOU 扩大写范围。
  3. 并发：落地因 CAS/重排失败或 prepare 期间路径被他人创建时，重读；已成为目录则返回 `created:false`。
  4. CLI `mega2 path provision --server <URL> <PATH>`：`LoadMode::None`（不读配置）；token 只从环境变量 `MEGA2_TOKEN` 读取并以 `Authorization: Bearer` 发送；无 argv token 选项；不跟随跨主机重定向；超时 30 s；输出一行（`created <path> (<commit>)` / `already exists <path>`），退出码 0；服务端错误原样打印 `<CODE>: …` 到 stderr，退出码 1。
  5. 无父首推到未开通路径继续拒绝（`MONO_PATH_UNINITIALIZED`）。
- **Alternatives considered:** 放开无父首推（拒绝：违背 issue 不变量）；Git push-option 显式开通（拒绝：未实现 `push-options`，Libra 0.23.46 无入口）；让 create-entry 自身幂等（拒绝：Libra pin 契约）；按目标路径授权（拒绝：窄 token 可创建全局可见的祖先容器）。
- **Consequences:** 新增一个写端点与一个 CLI 子命令；Libra 原生入口经 `DEP-FU-03` 移交。
- **Revisit when:** Libra 提供原生开通命令。

### ADR-FU-06: 全新栈产品写落点回落到惰性物化的一级根

- **Status:** Accepted
- **Context:** `resolve_trunk_land_path` 只接受已有 `main` ref 的非根祖先（E5）。
- **Decision:** 无候选时先对写路径调用 `classify_creation_path`：`NotAllowed` / `Invalid` 直接返回对应 `PathPolicyError`（HTTP 400，文本与 Git 面一致；写路径为 `/` 时按 `NotAllowed` 处理——API 不创建新顶层根）；`Allowed` 时对 `/<首段>` 调用既有 `materialize_path_refs`（与 advertise 同一原语，幂等）后返回该路径。**永不**物化 `import_dir` 或其子路径（分类已把它判为 `NotAllowed`；否则 attach 祖先预检会拒绝全部后续导入，`mono_storage.rs:843-882`），也**永不**物化嵌套 `import_dir`（如 `/third-party/vendor`）的严格祖先（`path_policy::is_import_dir_ancestor`，同一预检理由）：回落落点若是这样的祖先，则不物化、返回 `MONO_PATH_UNINITIALIZED`（先经开通动作建立更深的非 import 路径）。另设**无条件的 ImportRepo 命名空间守卫**：凡经 `MonoApiService` 的产品写（create / edit-save / delete / move / 开通），**每一个**被改写的规范路径操作数（move 的源与目的都算）组件级位于 `import_dir` 之下（含 `import_dir` 本身）时，在落点解析之前一律返回 `MONO_PATH_NOT_ALLOWED`，不论 `main@/third-party` 是否曾被物化、不论该路径是否刚被清理（有存活 `git_repo` 行的路径仍由 `api_handler` 分派给 `ImportApiService`，不受影响）。其它已有非根 tip 的写路径不经分类，行为不变。
- **Alternatives considered:** 落在 `/`（拒绝：B0 拒绝根路径写）；要求先 clone（拒绝：#25 痛点）。
- **Consequences:** create-entry / edit-save / delete-entry / move-entry 在全新栈上可用；根外路径的产品写从拓扑错误变为 `MONO_PATH_NOT_ALLOWED`（#29 跨面一致）。
- **Revisit when:** B0 允许根路径 API 写。

### ADR-FU-08: ImportRepo = 可增量更新的普通 Git 仓库（#26 选项 1）

- **Status:** Accepted
- **Context:** 四份文档承诺多分支、客户端 tag、持续跟随上游；`edit/save` 已能直接推进 ImportRepo ref；attach 挂载只是 `.gitkeep` 占位；`import_dir` 下树内容只由 attach 产生（Monorepo 推送与产品写不在 import 目录落地，ADR-FU-06 进一步保证不物化）。
- **Decision:**
  1. B3 attach 挂载幂等，以**持久的挂载来源记录**为据：首次挂载成功时在同一事务写一行 `audit_logs`（`action=create`、`target_type=repository`、`target_id=repo_id`、`metadata={kind:"import_repo.attach", path}`，经 `idx_audit_logs_target` 查询）。后续推送目标已是目录时，只有该仓库对该路径存在来源记录才走「跳过 `search_and_create_tree` 与根 commit、只写 ref」（队列行 `landed_commit_id` 取当前根 commit）；**存量挂载**（升级前无来源记录）按确定性规则惰性回填：叶子恰为只含一个 `.gitkeep` blob 的树，且该仓库已有 ≥1 条分支 ref → 视为既有挂载并在同一事务写入来源记录；其余情形（普通目录、文件、物化预检失败）→ `IMPORT_REPO_PATH_OCCUPIED`，根树不变。
  2. 分支 ref（B3 事务内）与 tag ref（`update_refs` 直写，条件语句）都按标准 receive-pack 语义 CAS：`Create` 要求 ref 不存在；`Update` 要求当前值 = `old_id`；`Delete` 维持既有 `remove_ref_if_unchanged`。失败 → `IMPORT_REPO_STALE_REF`；分支 CAS 失败回滚到 savepoint 并终态化队列行 `Failed`。
  3. 不做服务端 `denyNonFastForwards`：客户端 `--force` 的非 ff 更新按普通 Git 接受。
  4. 成败粒度：tag 命令逐 ref 独立（unpack 后直写，先于分支处理，与分支结果无关）；同一 push 内的**分支**命令作为一个批在同一 B3 事务内应用——任一分支 CAS/校验失败则本批全部分支 `ng`、无一更新（比 stock Git 的逐 ref 更严格，避免部分分支前进；`smart.rs:605-617` 现有「finalize 失败标记全部仍 ok 的分支」语义保持不变，不改协议层）。未广告 `atomic`。在用户文档声明。
  5. 客户端文案去掉 `attach B3 did not complete successfully: {Debug}`，改为 `ImportRepoError` 的 `<CODE>: …`；未知失败回落为不含 Debug 结构的通用句。
  6. 兼容：存量已挂载 ImportRepo 无需数据迁移即可接受后续推送（存量别名路径由 FU-15 规范化）；首推失败遗留的 `git_repo` 行（无分支 ref、无叶子）按首推处理。
  7. **import 根不是 ImportRepo：** 协议分派（`repo_handler_with_commands`）在 TP-08 规范化之后、任何 `git_repo` 查找或创建之前，调用叶子校验核心 `check_import_repo_leaf(config, canonical_path)`（拒绝含 NUL、不严格位于 `import_dir` 之下——即等于 `import_dir`——的路径）；路径等于 `import_dir` 的 Git 请求被拒（upload-pack 与 receive-pack 均为 400 `IMPORT_REPO_PATH_INVALID`），不产生行、ref、对象或根改写。TP-08 的旧别名行回退与自愈保持不变；存量别名行由 FU-15 迁移一次性规范化。升级前已存在的 `import_dir` 本身的 `git_repo` 行从此不再被服务（惰性，`DEFER-FU-09` 登记清除）。
- **Alternatives considered:** 选项 2「一次性导入 + `IMPORT_REPO_IMMUTABLE`」（拒绝：与四份文档和 `edit/save` 现状矛盾）；绕开队列写分支 ref（拒绝：失去 MonoWriteQueue 串行化与 reaper/收养语义）。
- **Consequences:** 更新推送不产生 Monorepo 根 commit；嵌套 ImportRepo 两种顺序都可导入（由 ADR-FU-10 的子仓检查约束清理）。
- **Revisit when:** 需要服务端强制 ff、保护分支或 `atomic`。

### ADR-FU-09: ImportRepo 清理 = 原子摘除（带栅栏与事务内审计）+ 锁外可续清扫

- **Status:** Accepted
- **Context:** #27 要求授权、可审计、幂等、之后不可 advertise/clone；允许延迟 GC。叶子只写根 ref，因此摘除走同一 attach 机制；Codex R1 指出 attach/detach 的队列身份、陈旧 attach、审计事务性与续做关联必须显式定义。
- **Decision:**
  1. **操作身份：** attach payload 增加 `op: AttachOp`（`Attach` | `Detach`，serde `default = Attach`，存量行兼容，无迁移）。detach 入队用 `detach_operation_id = sha256("import_repo.detach\0" + repo_id + "\0" + canonical_path)`（域分离；attach 的 `attach_operation_id` 不含该前缀）。同一 `repo_id` 的重复 detach 按 `(kind, path, operation_id)` 重放；重新导入得到新 `repo_id` → 新 id。
  2. **B3 detach（同一 `MONO_WRITE_LOCK` 事务，savepoint 包裹）：** 校验 `git_repo` 行 `id = payload.repo_id` 且规范 `repo_path = payload.repo_path`（否则按 `absent` 终态 `Done`，无写）；先以 `SELECT id FROM git_repo WHERE id=$1 FOR UPDATE` 锁住 P 自身的行，再在同一事务内检查子仓（`repo_path LIKE escape_like(path) || '/%' ESCAPE '\'`，绑定参数），存在即 `IMPORT_REPO_HAS_CHILDREN` 终态 `Failed`、无写。**祖先生命周期栅栏**（与第 5 条同属 FU-18）：子仓 `git_repo` 行的注册（`repo_handler_with_commands` 的 ReceivePack 分支，`protocol/mod.rs:269-277`）改为在同一事务内先对其全部祖先 ImportRepo 行取 `FOR SHARE`（按组件枚举祖先路径，绑定参数 `repo_path IN (...)`）再插入。两把行锁互斥，因此只有两种串行结局：子仓注册先提交 → detach 取得行锁后必看到子仓 → `HAS_CHILDREN`；detach 先取得行锁 → 子仓注册等待其提交后看到父行已删除 → 作为与父无关的独立新导入注册（等同清理之后的全新导入，以自己的叶子挂载）。叶子缺失（首推失败遗留）时 detach 跳过树改写，仍删除行并审计；仅当该仓库对该路径存在挂载来源记录（或满足 ADR-FU-08 第 1 条的存量规则）时，从根树移除叶子（新根 commit，ADR-FU-02 成帧），否则不改根树、只删行（普通目录永不被清理删除）；若 `import_dir` 之下的父目录因此变空则一并移除，`import_dir` 本身为空时保留 `.gitkeep`；删除该 `repo_id` 的 `import_refs` 与 `git_repo`；插入审计行（第 3 条）。任一步失败回滚到 savepoint、终态化 `Failed`，四类状态均不变。
  3. **审计：** `AuditStorage::log_audit_in_txn<C: ConnectionTrait>(conn, …)`（FU-13 引入，`log_audit` 改为委托它）。行值：`actor_type=human`、`actor_id=0`（保留值：storage-only 无数值用户 id）、`action=delete`、`target_type=repository`、`target_id=repo_id`、`metadata={kind:"import_repo.remove", cleanup_id, path, requester, phase}`；`cleanup_id` = 该 detach 的 `push_queue` 行 id；`requester` = token 名或 `anonymous`；不含 token。detach 行 `phase="detached"`（事务内）；清扫完成写 `phase="swept"` + 各表删除行数（锁外）。
  4. **清扫（锁外）：** 按 `repo_id` 分批删除 `git_commit` / `git_tree` / `git_blob` / `git_tag`（每条语句 ≤ 1000 行，依 `repo_id` 前导索引），受第 6 条的每请求预算约束；首次清理请求在 detach 后立即清扫，超出预算时返回 `pending`。
  5. **存活栅栏（覆盖全部 ImportRepo 元数据写入，含对象行）：** 统一原语 `lock_live_import_repo(txn, repo_id, canonical_path)` = `SELECT id FROM git_repo WHERE id=$1 AND repo_path=$2 FOR SHARE`（绑定参数）。以下每一次写都在自己的事务内先取该锁，行不存在 → `IMPORT_REPO_REMOVED`（「推送期间该 ImportRepo 已被清理，请重新推送以重新导入」），本次写不落任何行：`ImportRepo::traverses_tree_and_update_filepath` 的 `git_blob.file_path` 更新（`import_repo.rs:104-117,422-465`；先做一次存活检查，失败即在解引用任何对象之前返回，计算完成后在同一事务内取锁并更新，该函数中的 `unwrap()` 改为错误返回）；`ImportService::save_entry` 的每一批 `git_commit` / `git_tree` / `git_blob` / `git_tag` 插入（receive-pack unpack 与 `ImportApiService::save_file_edit` 共用，`import_service.rs:112-123`）；B3 attach（含更新模式）；`update_refs` 的 tag 写；`attach_to_monorepo_parent` 的仅删除分支写；`ImportApiService` 的 `edit/save` ref 更新、tag 创建（`git_tag` 行 + ref）、tag 删除（ref + `git_tag` 行）（`import_api_service.rs:374-416,459-502,540-549,684-714`）。行锁与 detach 的 `FOR UPDATE` / `DELETE FROM git_repo` 互斥：先取得共享锁的写事务提交后 detach 才能删除（这些行随后由第 4 条清扫删除）；detach 提交之后任何写都取锁失败而不落行。因此**不存在 detach 之后写入的元数据行**，`phase="swept"` 是终态，进程在任意时刻崩溃都不会留下清扫遗漏；对象存储中的 blob 字节在元数据写之前写入，按第 7 条保留。
  6. **续做（清理台账）：** 新表 `import_repo_cleanups`（FU-14 迁移）：`id`（= `cleanup_id` = detach 队列行 id，主键）、`path`、`repo_id`、`state`（`detached` | `swept`）、`requester`、`rows_deleted`（json）、`created_at`、`swept_at`；索引 `(path, state, id)`，续做查询固定为 `WHERE path = $1 AND state = 'detached' ORDER BY id ASC LIMIT 16`（走索引顺序、无排序步骤）。detach 在同一 B3 事务插入 `state=detached` 行（与审计行一起回滚）；清扫完成后按主键条件更新为 `swept`（`WHERE id=$1 AND state='detached'`，幂等）。清理入口在目标路径无存活 `git_repo` 行时，按 `(path, state='detached')` 索引查询待续做台账行（有界：每行对应一次 detach），按上述查询按 `id` 升序分页续做，**每个请求的工作预算固定**：至多处理 16 条台账行、至多执行 100 批清扫语句（≤ 100 000 行）；预算内完成则返回 `absent`，预算用尽仍有剩余则返回 `pending`（台账行保持 `detached`，下一次请求从最小 `id` 继续——台账本身即持久续做游标）；多次「清理 → 重新导入 → 清理」循环各有独立台账行。`audit_logs` 只作证据，不作运营查询。后台续做（reaper）仍为 `DEFER-FU-06`。
  7. 对象存储 blob 字节**不删除**（内容寻址、与 Monorepo 共享），文档声明保留策略（`DEFER-FU-01`）。
- **Alternatives considered:** 锁内同步删全部元数据（拒绝：成本随仓库规模增长，阻塞全局写）；`git_repo.deleted_at` 软删除列（拒绝：迁移 + 所有查找点加过滤）；改键到保留路径做墓碑（拒绝：隐式保留命名空间）；按 `audit_logs` JSON 字段续做（拒绝：无索引、随审计增长无界扫描，Codex R10）。
- **Consequences:** 清理不可撤销；detach 与清扫之间崩溃留下可续做的元数据行（同路径下次请求续做；后台续做 `DEFER-FU-06`）。
- **Revisit when:** Git 命名空间 GC 落地。

### ADR-FU-10: ImportRepo 清理 HTTP 契约（精确查找）

- **Status:** Accepted
- **Context:** 需要有鉴权、可发现的产品操作；`find_git_repo_like_path` 无组件边界、字符串拼接（Codex R1 P0）。
- **Decision:** `POST /api/v1/import-repo/remove`，请求 `{ "path": "/third-party/<owner>/<repo>" }`，只挂 storage-only 写路由，handler **不经** `api_handler` / `ImportApiService` 分派。
  1. ImportRepo 叶子校验（FU-18 引入于 `src/ceres/pack/path_policy.rs`，唯一实现）：核心 `check_import_repo_leaf(config, canonical_path)` 要求不含 NUL 且组件级**严格**位于 `import_dir` 之下（≠ `import_dir`）；协议分派在 TP-08 规范化后调用核心；清理 API 与运维 CLI 调用严格入口 `strict_import_repo_leaf_input(config, raw)`：先拒绝 NUL 与 `\`，再要求 `raw == canonicalize_mono_ref_path(raw)`（拒绝 `..`、重复斜杠、尾斜杠等别名），再调用核心 → 否则 `IMPORT_REPO_PATH_INVALID`（400）。
  2. （鉴权通过后）仓库查找只用 `find_git_repo_exact_match(canonical)`（sea-orm 绑定参数等值）；禁止 `find_git_repo_like_path` 与任何字符串拼接 SQL。
  3. 子仓检查：`repo_path LIKE escape_like(canonical) || '/%' ESCAPE '\'`（绑定参数）存在行 → `IMPORT_REPO_HAS_CHILDREN`（409），无写。
  4. 鉴权：在第 1 条的**语法**校验之后、第 2–3 条的任何仓库查询之前执行清理专用的 `authorize_import_repo_removal(git, headers, canonical)`（`src/api/api_write_auth.rs`）：`push_auth=token` 时要求有效且覆盖目标路径的 token（401/403）；`push_auth=none` 或缺失时**一律 403**（HTTP 面不提供匿名破坏性操作，#27 排除项；无鉴权部署改用 ADR-FU-11 的运维 CLI）；端点把鉴权失败改写为固定响应体（401 `authentication required`、403 `forbidden`，不回显路径；需要 `ApiError::status()` 访问器，`src/common/errors/api.rs`），未授权调用方对「不存在 / 叶子 / 有子仓的父」得到逐字节相同的响应，不泄漏存在性或拓扑。
  5. 请求 `{ path, cleanup_id? }` 两种语义，由请求显式区分：**新操作**（只给 `path`）——若 `path` 有存活仓库则 detach 它（新 `cleanup_id`），并在预算内清扫它与该路径其它待续台账；**续做**（给出上一次响应中的 `cleanup_id`）——只处理该台账行（必须属于该 `path`，按 `path` 鉴权），**永不** detach 任何存活仓库；台账行不存在或不属于该路径 → 404 `IMPORT_REPO_CLEANUP_NOT_FOUND`，已 `swept` → 200 `removed`（幂等）。输出 `200 { path, outcome, repo_id, cleanup_id }`，`outcome` ∈ `removed` / `pending`（已 detach 但清扫超出本次预算，客户端须带 `cleanup_id` 续做）/ `absent`（新操作时无存活仓库且无待续台账）。这样「R1 待续清扫期间同路径重新导入 R2，随后续做 R1」不会触及 R2。
- **Alternatives considered:** 扩展 `delete-entry`（拒绝：混淆 ImportRepo 内部删移契约）；`DELETE` + 路径参数（拒绝：多段路径需编码）。
- **Consequences:** 新端点进运行时 OpenAPI；review 形态不挂（`DEFER-FU-02`）；`push_auth=none` 部署的 HTTP 清理不可用，由 ADR-FU-11 覆盖。
- **Revisit when:** 需要可恢复的归档语义。

### ADR-FU-11: 运维 CLI `mega2 import-repo remove`

- **Status:** Accepted
- **Context:** HTTP 清理要求 token（ADR-FU-10）；#25–#27 的试用栈与默认评估栈是 `push_auth=none`，若无其它入口将无法清理（#27 AC1「授权的运维者」）。
- **Decision:** 新增子命令 `mega2 --config <path> import-repo remove --path <P> --yes`：`LoadMode::FullAppContext`（需要可读配置与数据库凭据——即服务器运维权限，这就是授权边界）；缺 `--yes` 拒绝执行（退出码 2、无写）；路径校验与服务入口与 HTTP 相同（ADR-FU-10 第 1–3 条，调用 FU-17 `remove_import_repo`）；审计 `requester="operator-cli"`；遇 `pending` 在进程内以返回的 `cleanup_id` 续做（每轮受同一预算约束，至多 `--max-rounds`，默认 1000 轮；续做永不 detach 存活仓库），最终输出 `removed <path> (repo_id=…)` / `absent <path>`，轮数用尽仍为 `pending` 则输出 `pending <path>` 并以退出码 3 结束；错误打印 `<CODE>: …`，退出码 1。
- **Alternatives considered:** 允许 `push_auth=none` 下匿名 HTTP 清理（拒绝：#27 排除）；为 none 形态引入单独的 admin token（拒绝：新配置面，超出本计划）。
- **Consequences:** 新子命令；需要服务器访问（`docker compose exec mega2 mega2 --config … import-repo remove …`）。
- **Revisit when:** 出现无服务器访问的运维者需求。

### 故障恢复矩阵

| 故障点 | 可接受残留 | 恢复动作 | 禁止结果 |
|---|---|---|---|
| 开通：prepare 与他人并发创建同一路径 | 无 | 重读；已为目录则 `created:false` | 重复目录项、500 |
| 开通：B3 CAS 失败 | 队列行 `Conflict`/重排 | 重 prepare + 重授权 | 部分写入的树、越权写 |
| 惰性物化：并发两次物化 | 无（`WHERE NOT EXISTS`） | 无需 | 两个 `main@/<root>` 行 |
| attach 分支 CAS 失败 | 新对象行已入库（可被下次推送复用） | 回滚到 savepoint（本批全部分支不更新），行终态 `Failed`，客户端 `IMPORT_REPO_STALE_REF` | 行残留 `Running`、部分分支前进 |
| tag CAS 失败 | 无 | 该 ref `ng`，其它 ref 独立 | tag 被静默覆盖 |
| detach：提交前任一步失败 | 无 | 整体回滚（含审计行），行终态 `Failed` | 叶子已删而 `git_repo` 仍在（或反之）、孤立审计行 |
| detach 已提交、清扫前崩溃 | 该 `repo_id` 的元数据行 | 同路径下次清理请求按 `(target_id, cleanup_id)` 续清扫 | 孤儿行无审计指针 |
| 陈旧会话或 API 请求在 detach 之后写 | 无（detach 之前写入的行已被清扫；之后的每批写取锁失败不落行） | 行锁栅栏拒绝（`IMPORT_REPO_REMOVED`），客户端重推即重新导入 | 叶子被重新挂载、任何行写入已删除仓库 |
| ref 写事务持锁时 detach 到达 | 无 | detach 等待该事务提交后再删除（其 ref 一并删除） | 清理后仍有 ref 行 |
| 清扫中途崩溃 | 部分元数据行 | 续做，按批幂等 | 删除其它 `repo_id` 的行 |
