# RustyVault → libvault crate 迁移计划（2026-08-20）

**模板版本:** `v2`（2026-07-29 起生效；本计划整份符合 `docs/plan/plan-template.md` v2）。

## 文档职责

本文解决「monoengine 内嵌的 vendored RustyVault 源码（`src/vault/` 顶层 module）改用 `libvault` crate 依赖」的迁移问题：移除 `src/vault/` 的 **82** 个 vendored `.rs` 文件与 `src/lib.rs` 的 `mod vault;`，引入 `libvault = "0.3.0"`（`storage_pg` + `crypto_adaptor_openssl`），把真实 `crate::vault::*` / `RvError` 引用改写为 `libvault::*`，并在**不修改上游源码**的前提下，用集成层重建与 UN-31 **等价**的只读语义（或经 spike 判定 no-go 后延后删除 vendored）。

关键判断（核对日 2026-08-20 / 复审 2026-08-21）：libvault 0.3.0 已发布且与 `../libvault-rs` 一致；vendored 与上游 `diff -rq` 约 81 行差异（含 Only in；核对日 2026-08-21），含 UN-31 只读、`RvError` 本地化、依赖版本面。**上游 `post_unseal` 无 readonly 分支**（见 VLT-S1 / ADR-VLT-02），因此「删 vendored」必须排在「只读可行性 go」之后，且实现卡与发布点卡分离（G-08）。

本文只规划任务，不宣称实现完成。

### 适用范围

- `src/vault/`（82 个 `.rs` + README + LICENSE）、`src/lib.rs` 的 `mod vault;` 与 `#[allow(...)]` 块。
- `src/common/errors/vault.rs`（本地 `RvError`）与 `src/common/errors/mod.rs` 重导出。
- 集成层真实消费 `crate::vault::` 的文件：`src/contract/vault/integration/vault_core.rs`、`src/contract/vault/pki.rs`。
- `RvError` 消费方（非 `crate::vault::` 路径）：`src/contract/vault/integration/jupiter_backend.rs`、`src/common/errors/`。
- 测试迁出：`src/vault/fix04_list_contract.rs`、`src/vault/un31_readonly.rs` → `src/contract/vault/integration/`（钉死落点，见 VLT-02）。
- 依赖面：根 `Cargo.toml` / `bin/Cargo.toml` 版本面（按卡 `Version increment` bump）+ `libvault = "0.3.0"`。
- 特性：`storage_pg` + `crypto_adaptor_openssl`。

### 非目标

- 不做 mega 的 `libvault-core` 0.1.0 迁移。
- 不做 libra 的 `libvault` 升级（已在仓外完成）。
- 不采用方案 A（vendored 同步到 0.3.0 继续 fork）——见 ADR-VLT-01 Alternatives。
- **默认不做上游 fork/补丁**（GC-VLT-01）。若 VLT-S1 判定公共 API 无法等价实现 UN-31，则 **no-go**：不删除 vendored，登记 `DEFER-VLT-01`，可另行向上游提 readonly 能力（那时再 revisit ADR）。
- 不改变 vault 表 schema、`core_key.json`、seal（10/5）、`secret/` 挂载路径。
- 不把 `src/context/`、`src/server/ssh_server.rs`、`src/config/`、`src/commands/`、`src/jupiter/storage/vault_storage.rs`、`src/callisto/` 当作 **`crate::vault::` 引用切换面**（它们消费集成层或 SeaORM `callisto::vault` 实体）。例外：go 路径下 `open_readonly` / `denied_writes` 签名面由 VLT-02/04 写集显式覆盖（见 VLT-02）。

### 成功定义

- `src/vault/` 删除（仅当 VLT-S1 = go），`crate::vault::` 在 `src/`/`bin/` 零命中（除 docs 历史）。
- `libvault = 0.3.0` 在 `Cargo.lock`；版本面按发布卡 bump 且两处一致。
- FIX-04 与 `un31_readonly` 测试迁到 `src/contract/vault/**` 且绿（只读用例在 VLT-04 解除 ignore）。
- 若 go：`VaultCore::open_readonly` 满足 UN-31 八条等价 AC；`un31_`（≥12 用例）/ `un43_readonly` 全绿；`REL-VLT-RO` 仅经 VLT-05 推送。
- 若 no-go：vendored 保留；本计划以 VLT-00/VLT-01/VLT-S1/`VLT-S2` 收口 + `DEFER-VLT-01`，不宣称方案 B 完成。
- 三门全绿；文档与 `plan-long` 原则 2 一致。

## 已决议设计决策

### ADR-VLT-01: 方案 B（crate 依赖）优先于方案 A（继续 vendored）

- **Status:** Accepted
- **Context:** vendored 与上游漂移；方案 A 永久 fork。
- **Decision:** 目标形态 = crates.io `libvault` 0.3.0 + `src/contract/vault/`。只读不进上游 fork（默认）。
- **Alternatives considered:** 方案 A——拒绝。向上游提 PR 增 readonly——允许作为 VLT-S1 no-go 后的 follow-up，不在本计划改 crates.io 包。
- **Consequences:** 删除 vendored 以 VLT-S1 = go 为前提；原则 2 保护的是 crate+集成层，不是永久 vendored。
- **Revisit when:** 上游增加 readonly，或 VLT-S1 no-go。

### ADR-VLT-02: 只读可行性门禁（spike 先于删除）

- **Status:** Accepted
- **Context:** 上游 `post_unseal`（`../libvault-rs/src/core.rs:608-631`）无条件 mount 修复/写与 auth init（含 expiration worker `auth/mod.rs:411-412`）。仅 `ReadonlyBackend` 只能「写时拒绝」，不满足 UN-31「写前具名 fail-closed」（`plan-20260812` UN-31 / Codex R1）。候选公共 API 路径仅为集成层 **shadow-unseal**（绕过 `Core::unseal`），范围大、易漂移。
- **Decision:** 新增 **VLT-S1（spike）**：在公共 API 上证明或证伪等价 UN-31。**go** → 继续 VLT-02/04/05（VLT-04 按 L-exception）。**no-go** → 不删除 vendored，经 **VLT-S2** 登记 `DEFER-VLT-01` 并推送落库，本计划不宣称方案 B 完成。
- **Alternatives considered:** 先删后补——拒绝（空窗 + 不可逆）。弱化 AC 为仅拦写——拒绝（GC-VLT-03）。
- **Consequences:** REL-VLT-RO 依赖 VLT-S1 go；spike 产物写入 `docs/refactoring/vault.md`；入库覆盖 go→VLT-05、no-go→VLT-S2。
- **Revisit when:** 上游 readonly 落地。
