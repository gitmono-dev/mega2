# Website 内部产品邮件 API 计划（2026-08-02）

**模板版本:** v2（成稿符合 `docs/plan/plan-template.md` v2）

## 文档职责

本文解决 **website 尚未提供** `POST /api/internal/notifications/email` 的缺口（`plan-20260731.md` 的 **DEP-06**）。monoengine 侧客户端、触发器接线与 compose bearer 占位已由 MN-05/MN-06 落地，但 website 仓仍只有认证事务邮件（`@libs/email`），无内部产品通知 API、无产品事件模板、无幂等受理。目标是：

1. 在 website `monoengine` 分支的 `apps/next-app` **实现**与 [`docs/refactoring/website-mail.md`](../refactoring/website-mail.md) 一致的内部邮件接口；
2. 用 `@libs/email` **扩展产品通知模板**，覆盖 monoengine 现行五类产品事件；
3. 提供 **IT 可验证**的投递路径（测试 provider 和/或 SMTP→mailpit），使栈级 compose 不再只能依赖 monoengine 侧 wire mock；
4. 在 monoengine 仓 **关闭 DEP-06**、同步文档与（若需）compose/CI pin，并留下可继承的验收证据。

本文只规划任务，不宣称实现完成。落地时每个任务都必须先刷新源码锚点，再按任务卡验收。

### 适用范围

- **Website（主写集）:** `apps/next-app/app/api/internal/notifications/email/`、`@libs/email` 产品模板与（若需）`smtp`/测试 provider、bearer 校验 helper、单元/路由测试、website 侧 AGENTS/README 短说明。
- **Monoengine（协调写集）:** `docs/refactoring/website-mail.md` / `notification.md` / `test-infra.md` / `integration.md` / `docs/plan/plan-long.md` / `docs/plan/README.md`；必要时 `docker-compose.test.yml`（website-next SMTP/provider env）、`.github/workflows/config-validation.yml` 的 website pin、可选 `bin/tests` 栈级邮件 IT。
- **契约:** 请求/响应/错误码/鉴权/幂等以 `website-mail.md` 为单一事实源；本计划可修订该契约，但必须同卡同步 monoengine 客户端期望。

### 非目标

- 不在 monoengine 恢复 SMTP / `[mail]` / `email_jobs`（ADR-WA-08 不变）。
- 不把 CL/issue 事件编排迁到 website；本计划只实现 **投递 API**。
- 不实现 website 侧持久 outbox / 跨进程重试队列（见 `DEFER-WE-01`）；本计划幂等为「受理去重」。
- 不实现 SendGrid/Mailchimp；生产仍用已有 Resend/Cloudflare。
- 不做 PT-12 全量前端对照；不改 Better Auth 会话路径。
- 不强制本计划内替换 monoengine 单元测试中的 wire mock（可并行保留）；栈级绿依赖真实 API。

### 成功定义

- website 暴露 `POST /api/internal/notifications/email`：Bearer 鉴权、必填 `Idempotency-Key`、JSON 形状与错误码符合 `website-mail.md`。
- 五类事件（`cl.comment.created` / `cl.merged` / `issue.comment.created` / `issue.closed` / `item.referenced`）均有产品模板；未知 `event_type` → `422 unsupported_event`。
- 相同 `Idempotency-Key` 重放返回同一 `delivery_id` 且 `duplicate: true`，不重复发送。
- IT：在 `--profile app --profile web` 栈上，monoengine 配置的 bearer 可调通 website API，并可用测试 provider 记录或 mailpit 捕获证明发送路径。
- `plan-20260731.md` DEP-06 标记为已由本计划交付；`plan-long.md` PT-09 更新；本计划全部非延后卡 `Lifecycle=done` 且 `Acceptance=complete`。

## 已决议设计决策

### ADR-WE-01: 契约冻结与仓库边界

- **Status:** Accepted
- **Context:** `website-mail.md` 已定义路径/鉴权/JSON；monoengine 客户端已按该契约实现；website 尚无实现。
- **Decision:** 以 `docs/refactoring/website-mail.md` 为跨仓契约唯一事实源。本计划默认 **不改** 路径、鉴权头、成功 `202` 形状与错误 `code` 表。若实现中发现不可行点，必须先改契约文档 + monoengine 客户端同批修订，不得单侧漂移。实现代码主落点在 **website** 仓库；monoengine 只改文档、compose/CI pin、可选栈级测试。
- **Alternatives considered:** 在 monoengine 再开代理 SMTP（拒绝——违反 ADR-WA-08）；把契约迁到 website 仓（拒绝——客户端与 IT 已绑定 monoengine 文档）。
- **Consequences:** website PR 必须引用本计划卡号与 `website-mail.md` 章节。
- **Revisit when:** 需要预渲染 HTML/附件或公开用户 API 时。

### ADR-WE-02: 鉴权只认共享 Bearer

- **Status:** Accepted
- **Context:** 产品邮件是服务间调用；Better Auth cookie 属于浏览器会话。
- **Decision:** 路由只接受 `Authorization: Bearer <token>`，与 `MONOENGINE_INTERNAL_MAIL_BEARER`（website）/ `MEGA_NOTIFICATION__WEBSITE_MAIL_BEARER`（monoengine IT）对称。使用 constant-time 比较；缺省/错误 → `401 unauthorized`。**禁止**接受 session cookie、公开 API key 或无鉴权。生产 bearer 经 website 受控 env / secret 注入，不得写入示例仓库明文生产值。
- **Alternatives considered:** mTLS（拒绝——本计划过重）；复用 get-session cookie（拒绝——错误信任边界）。
- **Consequences:** compose 已有 IT 明文 bearer（公开测试值）；生产轮换窗口见 `DEFER-WE-02`。
- **Revisit when:** 需要短期双 key 轮换时。

### ADR-WE-03: 事件 allowlist 与模板归属

- **Status:** Accepted
- **Context:** monoengine 触发器固定五类 `event_type`；website 现只有 auth 模板。
- **Decision:** 本计划最小 allowlist 即为：`cl.comment.created`、`cl.merged`、`issue.comment.created`、`issue.closed`、`item.referenced`。每种事件一份 MJML→编译 HTML 产品模板（`en` + `zh-CN`），由 website 渲染；monoengine 只传契约 `payload` 业务字段。未知事件 → `422` + `unsupported_event`。payload 缺必填字段 → `422` + `invalid_payload`。
- **Alternatives considered:** 接受任意 event_type 并用通用模板（拒绝——不可审计）；在 monoengine 渲染 HTML（拒绝——已删本仓模板）。
- **Consequences:** 新增事件类型需同步 website 模板与本 allowlist 文档。
- **Revisit when:** PT-09 扩展更多通知类型时。

### ADR-WE-04: 幂等与发送时机

- **Status:** Accepted
- **Context:** 契约（`website-mail.md` §2.1）要求同一 `Idempotency-Key` 重放返回同一受理结果且**不得重复发送**。
- **Decision:** 采用三态记录 `(bearer-scope, Idempotency-Key)` → `{delivery_id, fingerprint, state}`，`state ∈ {in_progress, succeeded, failed}`（存储：website-next IT 默认 SQLite 表或等价；单测可用内存 store）：
  1. **首次：** 原子插入 `in_progress` + 新 `delivery_id` + body fingerprint（唯一约束冲突则走重放分支）；再调用 `@libs/email` 发送；成功则把 state 更新为 `succeeded` 并返回 `202` `{duplicate:false}`；发送失败则更新为 `failed`（或删除 in_progress 行）并返回 5xx，允许调用方用**同一 key**重试。
  2. **重放 `succeeded` + 同 fingerprint：** `202` `{duplicate:true}`，**零次**再次调用 provider。
  3. **重放 `succeeded`/`in_progress` + 不同 fingerprint：** `409 idempotency_conflict`。
  4. **重放 `in_progress`：** 返回 `409` 或有界等待后读最终态（本卡选：**立即 `409 idempotency_conflict` 对异请求；同 fingerprint 的并发第二者在唯一约束上失败后轮询/读到 succeeded 再回 duplicate**——实现须保证 provider 至多调用一次）。
  5. **重放 `failed`：** 视为可重试：转回 `in_progress` 再发送一次。
- **Alternatives considered:** 仅成功后写入（拒绝——竞态可双发，违反契约）；失败也标 succeeded（拒绝——永久吞掉重试）。
- **Consequences:** 必须用唯一约束 + 状态机保证「同 key 至多一次成功发送」；多实例跨进程见 `DEFER-WE-01`。
- **Revisit when:** 引入独立邮件 outbox worker 时。

### ADR-WE-05: IT 投递后端

- **Status:** Accepted
- **Context:** 生产用 Resend/Cloudflare；`smtp` 未实现；compose 已有 mailpit。
- **Decision:** 本计划交付 **`EMAIL_PROVIDER=test`（或等价）记录型 provider**：`sendEmail` 成功并写入可查询的内存/文件/表记录，供单元与栈级断言；**另**实现最小 `smtp` provider 指向 `mailpit:1025`，供可选捕获。compose `website-next` 默认 IT 使用 `test` provider（稳定、不依赖外网）；需要捕获时再切 `smtp` + mailpit。**禁止** IT 默认依赖真实 Resend/Cloudflare 云调用。
- **Alternatives considered:** 只做 smtp（拒绝——CI 脆弱且当前 stub）；只做 mock 路由不调用 `@libs/email`（拒绝——绕过真实发送栈）。
- **Consequences:** WE-05 必须先于 WE-06 的栈级绿。
- **Revisit when:** website 统一测试邮件策略变更时。


### ADR-WE-06: 跨仓发布模型（website 家族 + monoengine 家族）

- **Status:** Accepted
- **Context:** `WE-02..WE-05` 为 website 仓 `implementation` 卡，模板 `G-07` 禁止对 implementation 使用 `no-release`；同时又不能与 monoengine `Cargo.toml` 版本面混发。
- **Decision:** 本计划使用**两个**发布家族：
  1. **`REL-WE-SITE`**：唯一发布点卡 `REL-WE-SITE`；成员 `WE-02..WE-05`（`family child`）。C 组为 website-native：focused `pnpm` 测试 → 在 website 仓提交并推送 `monoengine` 分支 tip → 记录 tip SHA 到本计划 Review/验收证据。`Version increment: N/A`（不碰 monoengine 版本面）。
  2. **`REL-WE-01`**：唯一发布点卡 `REL-WE-01`；成员改 monoengine 的 `WE-06`（及必要 FIX）；`WE-01`/`WE-07` 为 `no-release` 并继承其 C/D。C 组为 monoengine `patch` bump + AGENTS 三门 + push `main`。
  顺序：先完成 `REL-WE-SITE`（website tip 可用），再 `WE-06` pin 该 SHA，再 `WE-07`，最后 `REL-WE-01`。
- **Alternatives considered:** 全部标 `no-release`（拒绝——违反 G-07）；把实现细节挪出本计划只留 handoff（拒绝——削弱可执行任务卡）。
- **Consequences:** 两仓推送由同一发布者串行执行（ER-12）；禁止在 `REL-WE-SITE` 未完成时更新 monoengine CI pin。
- **Revisit when:** website 仓引入独立日期计划模板时。
