## 文档职责

本文承接上游 **git-internal 0.9.0** 的 BLAKE3 / 显式 `HashKind` 契约（handoff：`docs/development/blake3-integration.md` §9 / §12），关闭 `plan-20260903` 的 **DEFER-HSH-02**（及本仓范围内 DEFER-HSH-01 / DEFER-HSH-03 的可交付部分）。目标是交付：**mega2 以显式 repository `HashKind` 解析与计算全部 Object ID**（禁止 `ObjectHash::from_str` / 长度推断把 64 hex BLAKE3 静默标成 SHA-256）；**Buck 契约仍为 `sha1:40HEX` 且解析收紧**；**`monorepo.object_format=blake3` 可 bootstrap，并可在 Libra/git-internal peer 上完成 protocol/pack 服务**；**不宣称标准 Git 互通、不做原地 migration**。

本文只规划任务，不宣称实现完成。落地时每个任务都必须先刷新源码锚点（GC-01），再按任务卡验收。

### 适用范围

- `Cargo.toml` / `Cargo.lock` 将 `git-internal` 钉到 **0.9.0**（crates.io）。
- 穷举 `HashKind` / `ObjectHash` / `HashAlgorithm` 等新增 `Blake3` 分支的编译收口。
- 生产路径消除 `ObjectHash::from_str` / `from_bytes_infer_kind` 与「仅靠 40/64 长度推断 kind」的 ObjectHash 解析。
- Buck `parse_sha1_hash` 收紧为 `from_hex_for_kind(Sha1, …)`。
- 进程级权威 kind：`MonoConfig.object_format` → `object_hash_kind()`；协议 / pack 入口注入该 kind（覆写 `RepositoryAccess::object_hash_kind` 若接入，否则等价注入 SmartSession / `RepoHandler`）。
- `service init --yes` 的 `object_format=blake3` bootstrap（类比既有 SHA-256 bootstrap）。
- Smart HTTP/SSH / pack 对 `object-format=blake3` 的协商与 `*_with_hash_kind` 编解码；同一 plumbing 上可将 SHA-256 提升为 normal service（ADR-B3-05）。
- Hash domain 边界：Git Object Format 与 LFS Digest Algorithm 独立建模、独立协商、独立校验；`Git=blake3/LFS=sha256` 与 `Git=sha256/LFS=blake3` 均必须可表达。
- 文档：扩展标记、非互通边界、索引与 DEFER 关闭说明。

### 非目标

- **不实现** 标准 Git upstream BLAKE3 互通（永久非目标；DEFER-B3-01）。
- **不做** 既有 SHA-1/SHA-256 仓库的原地 migration / 隐式转换（永久非目标）。
- **不改** AI / 应用层固定 SHA-256 digest 契约（handoff §6）与 Buck manifest 表面（仍 `sha1:40HEX`，只修解析器）。
- **不重做** git-internal 已交付的 hasher / tagged ID / pack idx / protocol 协商内核。
- **不 bump minor/major**；实现/release 卡一律 **patch +1**（文档卡 `N/A`）。
- **不把**「0.9.0 能编译」与「BLAKE3 peer clone E2E」压进同一张卡（G-01）。

### 成功定义

- tip 钉 `git-internal = "0.9.0"`；实现卡各自 patch 发布后三门绿。
- 生产路径 `ObjectHash::from_str` / `from_bytes_infer_kind` 零命中（B3-01 守卫）。
- Buck：`sha1:`+40 hex → Sha1；`sha1:`+64 hex 拒绝。

## 已决议设计决策

### ADR-B3-01: 禁止以长度推断 ObjectHash kind

**决策：** Object ID 解析/构造必须带显式 `HashKind`（`from_hex_for_kind` / `*_with_kind` / `*_for_kind`）。生产路径禁止 `ObjectHash::from_str` / `from_bytes_infer_kind`。`is_full_hex_object_id` 若保留 40|64 形似检查，注释必须写明 **长度≠kind**。

### ADR-B3-02: 无原地 migration；无标准 Git 互通宣称

**决策：** 既有仓不转换格式。`object-format=blake3` 标记为 git-internal/Libra extension。

### ADR-B3-03: Buck 与固定 SHA-256 digest 契约不变

**决策：** Buck 仍仅 `sha1:40HEX`；解析改为 `from_hex_for_kind(Sha1, …)`。应用层固定 SHA-256 digest（handoff §6）不改为 BLAKE3。

### ADR-B3-04: 权威 kind = 进程 `monorepo.object_format`

**决策：** 以 `MonoConfig.object_hash_kind()` 为权威。SmartSession / pack / converter / API 消费该 kind。多格式并存另开计划（DEFER-B3-02）。接入 `RepositoryAccess` 时必须覆写 `object_hash_kind()`。

### ADR-B3-05: Bootstrap 与 normal service 分阶段

**决策：** B3-03 仅打开 blake3 bootstrap（normal service 仍拒）。B3-04 完成 wire/pack 后打开 blake3 normal service；推荐同卡打开 sha256 normal service（同一 plumbing），否则登记明确 DEFER。

### ADR-B3-06: 升级机械清扫使用 G-04 豁免

**决策：** B3-01 登记 **EX-B3-01**（`L-exception:EX-B3-01`）。

### ADR-B3-07: Git Object Format 与 LFS Digest 独立组合

**决策：** Git repository 的 Object Format 与 LFS Digest Algorithm 是两个独立字段和 hash domain。至少 `Git=blake3/LFS=sha256` 与 `Git=sha256/LFS=blake3` 必须可表达和验证；`MonoConfig.object_format` 不得隐式覆盖 LFS digest。标准 LFS fallback 仍使用自身的 `sha256:` 语义。本计划只交付组合边界和 fail-closed plumbing，LFS BLAKE3 业务面由 DEFER-B3-LFS-01 承接。

## 全局工程约束

- **GC-B3-01：** 生产路径零 `ObjectHash::from_str` / `from_bytes_infer_kind`（B3-01 后持续）。
