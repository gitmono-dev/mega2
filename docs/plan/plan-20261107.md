# docker login 接入用户 token 计划（2026-11-07）

## 文档职责

本文解决 storage-only OCI `docker login` 只认 `[[git.push_tokens]]`、megaui 签发的 Mono `access_token` 无法登录镜像仓库的缺口。目标是：同一 mega2 进程在配置了 website 会话时，让已有的 token 创建/吊销 API 写入 `access_token`，并且 `/v2` 把该明文当作 Basic 密码或 Bearer 在本地验过。

本文只规划任务，不宣称实现完成。落地时每个任务都必须先刷新源码锚点，再按任务卡验收。

**模板版本:** `v2.5`

**任务前缀:** `OCR`（OCI registry 用户凭据）。`ADR-OCR`、`DEFER-OCR`、`DEP-OCR` 同前缀。不占用 `plan-20260902.md` 的 `DR-*`。

### 适用范围

- storage-only 且 `[oci].enabled=true` 时的 `/v2` 认证
- 同一进程上、仅当 `oci.accept_user_tokens=true` 且 `[oauth].website_api_base_url` 非空时挂载的三个 token 端点。该开关不改变 `/v2` 是否接受 access token
- `docs/refactoring/oci.md`、`docs/deploy-trunk.md`、`docs/refactoring/website-auth.md`、`config/config.toml` 注释

### 非目标

- 不新增 OCI token 服务，不协商 scope，不改 `WWW-Authenticate` 挑战文本
- `docker login` 时 mega2 不回调 megaui。megaui 只在创建或吊销 token 的会话解析里被访问
- 不把用户 token 在 `push_auth=token` 下授权到整库。该模式下 repo 第一段不等于该用户名时，读和写都是 `DENIED`。`push_auth=none` 的读和写都不按用户名缩范围
- 不改变 `[[git.push_tokens]]` 的 `paths` 语义
- 不把用户 token 接到 `push_auth=token` 的 Git HTTP 或 LFS
- 不挂载 SSH key 或通知偏好路由
- 不修改 megaui。登录命令展示由 `../megaui/docs/plan/plan-20261107-docker-login.md` 承接

### 成功定义

- `anonymous_access=false` 且 `push_auth=token` 时，恰好一行且用户名非空的 access token 使 `GET /v2/` 返回 200。ping 不是仓库读
- `push_auth=token` 时，该用户只能读和写第一段等于自己用户名的 repo。用户名不是合法 OCI 分量时，没有仓库的第一段能等于它，写由「第一段不同则 DENIED」覆盖
- OCR-01 发布后、OCR-03 发布前，两种 `push_auth` 下用户 token 的仓库读都是 `DENIED`。`push_auth=none` 的写仍不看凭据。OCR-03 再放开：`push_auth=none` 的读不按用户名缩范围，mount 源在读授权通过后成功。`GET /v2/` 上的无效秘密仍是 401
- 删除该行后，该秘密无法匹配。这与 OCR-01「无法匹配则 401」是同一条验收，不单列
- `git.storage_only()==true` 且 `[oci].enabled` 不为 true 时不挂 `/v2`。token 路由还要 `oci.accept_user_tokens=true`。没有该开关，或没有非空 website 基址，都不挂 token 路由，会话保持匿名。`/v2` 是否接受 access token 不看这个开关。review 形态不能打开 OCI，并继续注册既有 token 路由
- 三张卡 `Lifecycle=done` 且 `Acceptance=complete`。计划正文的 Claude 与 Codex 审查均为 `PASS`

## 已决议设计决策

### ADR-OCR-01: OCI 本地接受 Mono access token

- **Status:** Accepted
- **Context:** `docker login` 把密码放在 Basic 里。今天写授权只调用 `lookup_push_token`。megaui 的 token 已写入 `access_token`。
- **Decision:** 每次 `/v2` 请求把凭据解析为：缺失、非法、静态 token、用户 token。先做静态常数时间匹配。命中则不再查库。未命中才调用 `UserStorage::authenticate_traces_access_token`。零行、两行、空用户名都是 `None`，与无法匹配同一结果。这个解析不看 `[oauth]`。静态 token 的写仍走 `token_covers_repo("/" + repo)`。`push_auth=none` 的写不看凭据。`push_auth=token` 的最终语义在 OCR-03：用户 token 的读和写都要求 repo 第一段等于用户名。OCR-01 单独发布时还没有这条范围，该模式下用户 token 的读和写都是 `DENIED`。用户名是合法分量当且仅当它不含 `/` 且 `valid_repository_name(用户名)` 为真。`src/common/oci_name.rs:17` 的正则允许 `/`，不能单独当分量判断。OCR-03 在同文件增加 `valid_repository_component`。不是合法分量时，OCR-03 下该用户 token 的写是 `DENIED`。跨仓 mount 的目标用写规则。源按凭据种类分开：静态 token 仍走 `token_covers_repo`，不改变 `paths` 语义。用户 token 的源用用户 token 的读规则。`src/api/router/oci_router.rs:477` 只把用户 token 从「直接 401」改成这条读规则。`push_auth=none` 的读不按用户名缩范围：有效凭据按今天的 `authorize_read` 放行，匿名读仍只看 `anonymous_access`。该模式下 mount 源在读授权通过后直接成功，不检查第一段，也不检查 `paths`。第一段与 `paths` 检查只在 `push_auth=token`。展示名碰撞沿用 `docs/refactoring/website-auth.md:89`，不新建映射表。删除 token 行之后，该秘密变成无法匹配。
- **Alternatives considered:** 新表或新 token 服务被拒绝，ADR-DR-02 已拒绝独立 token 服务。把用户 token 当成空 `paths` 的静态 token 被拒绝，那会授予整库写。静态命中后仍查库被拒绝，避免热路径为 CI token 增加一次数据库往返。
- **Consequences:** Git HTTP 在 `push_auth=token` 时仍不认 access token。同一秘密若同时出现在配置和表里，身份是静态 token 的 `name`。静态命中比未命中少一次查询。
- **Revisit when:** 需要按团队或 Cedar 授权 OCI repo。

### ADR-OCR-02: 查库失败与匿名读

- **Status:** Accepted
- **Context:** 匿名读开启时，不带凭据的 ping 必须仍是 200。带了错误密码必须 401，否则 `docker login` 无法暴露失败。见 `tests/integration_oci.rs:552`。
- **Decision:** 对 `GET /v2/`：非法头、空密码、两种凭据都未命中、用户 token 多行，全部 `OciError::Unauthorized`。查库返回 `Err` 时同样 401，并用 `tracing::error` 记录错误。日志与响应体都不含 token 原文。`push_auth=none` 的写请求保持今天的行为：不看凭据，直接放行。不新增 OCI 错误码。挑战头保持 `src/ceres/oci/error.rs:8` 的现文。
- **Alternatives considered:** 查库失败返回 500。拒绝，因为现有枚举没有内部错误变体，Docker 会把非 401 显示成协议失败。
- **Consequences:** 数据库中断时登录表现为认证失败。操作者看服务端日志区分。
- **Revisit when:** OCI 错误枚举增加稳定的内部错误码。

### ADR-OCR-03: token 路由只在 OCI 进程配置了 website 会话时出现

- **Status:** Accepted
- **Context:** `/v2` 只挂在 storage-only。该形态今天强制匿名会话，且不挂 `/api/v1/user`。megaui 创建 token 依赖 website `get-session`。
- **Decision:** 只在 `git.storage_only()==true` 时考虑 token 路由。还要同时满足 `oci.enabled==true`、`oci.accept_user_tokens==true`，以及存在 `[oauth]` 节且 `website_api_base_url` 非空，才把 `BrowserSessionStore` 改成 `WebsiteSessionStore`，并挂三个 token 路由。`accept_user_tokens` 默认 false。默认 `config/config.toml:351` 已是 storage-only，`:201` 已有非空 website 基址；评估用 compose 只打开 `oci.enabled`，不设置 `accept_user_tokens`，因此不切换会话，也不暴露 token 路由。没有 `[oauth]` 节，或 `oci.enabled` 不为 true，同样保持匿名会话。`[oauth]` 存在但基址为空会在 `validate.rs:250` 拒绝启动。review 形态继续用 `http_server.rs:845` 的 `WebsiteSessionStore` 和原有 `user_router::routers()`。不挂 SSH、通知或 `GET /user`。website 会话 cookie 能让 generate 插入一行；匿名会话不能。没有 cookie 时两种会话都是 401，不能用来区分它们。
- **Alternatives considered:** 登录时回调 megaui。拒绝，登录只读本地表。所有 storage-only 都挂 token 路由。拒绝，没有会话源就无法知道用户名。
- **Consequences:** megaui 的 mega2 基址必须指向这个同时提供 `/v2` 与 token API 的进程，并且共用一个 Postgres。该约束写进 `docs/deploy-trunk.md`。
- **Revisit when:** review 与 storage-only 合并为单一进程形态。
