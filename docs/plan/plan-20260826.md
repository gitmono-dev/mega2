## 已决议设计决策

### ADR-SYNC-01: LFS limit 解析为 usize + "Invalid" 前缀穿透保 400 分类

- **Status:** Accepted
- **Context:** `limit` 来自查询字符串；`parse::<i64>()` 允许负数，`-1 as usize` 越界索引触发 panic；且 `lfs_retrieve_lock` 把所有错误掩成 `"Lookup operation failed!"`，`map_lfs_error` 因此把非法参数误判为 500。
- **Decision:** 抽出纯函数 `apply_lock_limit`，把 limit 直接 `parse::<usize>()`（天然拒绝负数与非数字），`min(size, len)` 后 `split_off`；**空 `limit`（`""` / 未提供）在函数内先于 parse 短路**（`if !limit.is_empty()`，与 mega 一致），视为「不分页、返回全部」，不视为非法输入；`lfs_retrieve_lock` 对 `msg.starts_with("Invalid")` 的 `GeneralError` 原样穿透，其余仍掩码，使 router 的 `map_lfs_error` 按既有 "Invalid" 前缀逻辑返回 400。实现按轴拆到 SYNC-01（校验/分页）与 SYNC-04（错误分类）。
- **Alternatives considered:** 在 router 层加类型化错误变体——更彻底但扩面到 `GitLFSError` 枚举与所有调用点，超出单卡行为轴；按 `String` 前缀穿透是 mega 已验证的最小面。
- **Consequences:** 错误契约仍依赖消息前缀（既有 TODO 已知脆弱），但不劣化现状；未来可另立卡把 `GitLFSError` 类型化。
- **Revisit when:** 决定重构 `GitLFSError` 为类型化变体时。

### ADR-SYNC-02: tree_ops 返回 .gitkeep blob，由调用方在 attach 前持久化

- **Status:** Accepted
- **Context:** `search_and_create_tree` 为新建路径生成占位 `.gitkeep` blob 并嵌入 leaf tree，但调用方只保存 trees/commits，blob 从不落对象存储，导致 clone/fetch 404。
- **Decision:** 返回类型改为 `(VecDeque<Tree>, Blob)`，`import_repo.rs` 在 `attach_to_monorepo_parent_in_txn` 之前调用 `mono_service.save_blobs(&new_commit.id.to_string(), vec![gitkeep_blob])`（沿用其「先写对象存储再写 mega_blob 行」的既有原子顺序）；tree/commit/CAS 逻辑不变。
- **Alternatives considered:** 把 blob 保存塞进 `attach_to_monorepo_parent_in_txn` 内——会扩大该 storage 函数的职责并破坏与调用方的单轴边界；由调用方负责更贴近 mega 的 `post_receive/import.rs` 与 `mono/sync.rs` 两处改法。
- **Consequences:** 调用方必须记得持久化返回的 blob；当前仅 `import_repo.rs:526` 一个调用点，`tree_ops.rs` 文档注释会标注该约束。
- **Revisit when:** 出现第二个 `search_and_create_tree` 调用方时，评估把「trees+blob 一起持久化」下沉为 storage 层方法。

### ADR-SYNC-03: CL 列表 build_status 采用 mega worst-wins 聚合，ItemRes 追加 Option 字段

- **Status:** Accepted
- **Context:** mega #2163 为 CL 列表聚合 Orion 构建状态；mega2 `ItemRes` 为 issue/CL 共用 DTO，无该字段。
- **Decision:** 在 `cl_storage.rs` 移植 `latest_build_status_by_cl_links(links) -> Result<HashMap<String,String>>`（`orion_tasks` 按 `cl` 取 `created_at` 最新 task → `build_targets` 按 `task_id` → worst-wins 聚合 `Failed > Interrupted > Building > Pending/Uninitialized > Completed`）——SYNC-03；`ItemRes` 追加 `build_status: Option<String>`（serde 缺省 `None`，issue 与无构建数据 CL 不受影响）并由 `fetch_cl_list` 批量查询回填——SYNC-05，避免 N+1。
- **Alternatives considered:** 在 `get_cl_list` 内联 join——会与分页/去重逻辑纠缠；独立批量方法保持单轴。
- **Consequences:** `/cl` 列表 JSON 新增可空字段，属加性变更，对既有消费者兼容；OpenAPI schema 由 `utoipa` 运行时自动反映。
- **Revisit when:** 需要把构建状态提升为列表排序/过滤维度时。
