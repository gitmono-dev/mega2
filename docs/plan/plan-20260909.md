# Storage-only LFS（`push_auth=none` / `token`）计划（2026-09-09）

> **改名註記（2026-09-17）：** 本文成稿與執行時，Cargo 包名／二進制名為舊名，lib 為舊名 `_core`；2026-09-17 起全倉統一改名為 **Mega2**（`mega2` / `mega2_core`），本文中的命令、路徑、環境變量與服務名已同步更新，歷史提交記錄本身不變。

**模板版本：** v2；依据 [`plan-template.md`](plan-template.md)，核对日期 2026-09-09。

## 文档职责

本文解决「trunk / storage-only 形态下 Git LFS 不可用」的缺口：今天 LFS 批/锁只认 `UserStorage` mono access token，且 `push_policy=trunk` 硬关闭路由，导致无用户系统的 storage-only 部署无法完成含 LFS 指针的推送与拉取。目标是交付：**LFS 写授权与 Git receive-pack 共用 `git.push_auth`（`none` 匿名可写、`token` 用 `[[git.push_tokens]]` + 组件边界 `paths`），review 形态保持现有 `UserStorage` 逻辑不变，并在 trunk HTTP 表面重新挂载 `/info/lfs` 与 `/api/v1/lfs`，附带进程级往返测试与部署文档反向声明**。

本文只规划任务，不宣称实现完成。落地时每个任务都必须先刷新源码锚点，再按任务卡验收。

### 适用范围

- LFS HTTP 批/锁鉴权闸门（`objects/batch`、locks；不含改写 object 能力 URL 模型）。
- Trunk / storage-only HTTP 路由挂载与 OpenAPI 表面（`/info/lfs`、`/api/v1/lfs`）。
- 与 `push_auth=none` / `push_auth=token` 对齐的策略矩阵与单测。
- storage-only 下 LFS push → fetch → `git lfs pull` 进程级集成测试。
- 部署与产品文档：`docs/deploy-trunk.md`、`docs/monorepo.md`、`docs/refactoring/protocol.md`、`docs/refactoring/trunk-push.md`（LFS 不可用声明 supersede）、`docs/refactoring/integration.md`、本目录 `README.md`。

### 非目标

- 不引入 Cedar / 用户系统 / OAuth 到 storage-only LFS。
- 不改变 review 形态的 `UserStorage` LFS 鉴权。
- 不实现 SSH `git-lfs-transfer`；storage-only 下 SSH receive-pack 仍关闭；LFS 走 HTTP（含既有 hybrid `git-lfs-authenticate` 若 SSH 仍监听 upload-pack——本计划不扩展 SSH 凭据体系）。
- 不重开 DEFER-TP-05（多 token 运维强化：轮换、审计、限流）。
- 不改 LFS 对象存储后端、内容定址校验、或 capability URL「batch 注册后 PUT/GET 不逐请求鉴权」模型。
- 不把 plan-20260905 的 TP-18「关闭 LFS」历史验收改写为失败；本计划 **supersede** 该产品决策。

### 成功定义

- `push_policy=trunk` + `push_auth=none`：匿名客户端可完成 LFS upload batch / lock 写与后续 pointer 推送所需的对象上传（与匿名 receive-pack 同一网络前提）。
- `push_policy=trunk` + `push_auth=token`：出示有效 `[[git.push_tokens]]` 密文可写；无 token 或 `paths` 不覆盖 `LfsRepoContext` 路径则写失败（401/403）；读仍可遵循 `git.anonymous_access`。
- `push_policy=review`（省略 `push_auth`）：LFS 行为与今日一致（写需 mono access token）。
- Trunk HTTP 挂载 `/info/lfs` 与 `/api/v1/lfs`；OpenAPI 如实列出；不再返回 `push_policy=trunk: LFS is review-only` 404。
- 部署文档删除「LFS 仅 review」；`monorepo.md` §8 表 trunk 列改为「可用（`push_auth`）」。
- 全部非延后任务卡 `Lifecycle=done` 且 `Acceptance=complete`；计划级 Codex/Claude 双评审对本计划文档 PASS；实现阶段另走每卡 ER-05。

## 已决议设计决策

### ADR-LF-01: LFS 写授权对齐 `git.push_auth`

- **Status:** Accepted
- **Context:** Trunk 无 `UserStorage`；receive-pack 已有 `token`/`none`；LFS 写仍走用户 token 导致 GAP-LF-02。
- **Decision:** 当 `push_policy=trunk`（storage-only 启动强制显式 `push_auth`）时：`push_auth=none` → Read/Write 均放行；`push_auth=token` → 用与 Git HTTP 相同的 Bearer/Basic 密文解析，经 `lookup_push_token` 认证；Write 另要求 `token_covers_repo`（或等价公开 helper）覆盖 `LfsRepoContext` 路径（空前缀视为 `/`，仅全库 token）。Read 在 token 形态下仍允许 `anonymous_access || authenticated`。省略 `push_auth` 的 review 形态保持 `UserStorage` 现状。
- **Alternatives considered:** (1) 仅 `none` 开 LFS——拒绝，因生产 storage-only 常用 `token`；(2) 为 LFS 另造配置键——拒绝，违反 GC-02 / 与 push 分叉。
- **Consequences:** 必须把 `token_covers_repo` 提成 `pub(crate)`（或迁到 `config` 旁单一事实源）供 `lfs_router` 使用，禁止复制组件边界算法。
- **Revisit when:** DEFER-TP-05 多 token 运维规范落地，或需 per-OID ACL。

### ADR-LF-02: `push_auth=none` 下匿名 LFS 写合法

- **Status:** Accepted
- **Context:** 用户目标含「不使用任何权限即可 LFS 提交」；与 `push_auth=none` 匿名 receive-pack 一致。
- **Decision:** trunk + `none` 时 LFS Write 不要求凭据；安全边界完全依赖部署网络（受控内网/回环/Unix socket），部署文档必须保留与 receive-pack 同级警告。
- **Alternatives considered:** none 下仍强制 token——拒绝，违背 storage-only 匿名形态。
- **Consequences:** 公网暴露 `none` = 匿名 LFS 上传 + 匿名 push；启动既有警告覆盖。
- **Revisit when:** 需要在 none 上叠加边缘代理鉴权时。

### ADR-LF-03: Object 能力 URL 与 review 回归不变

- **Status:** Accepted
- **Context:** `PUT`/`GET /objects/{oid}` 故意不逐请求鉴权；改之会弄断 git-lfs 客户端。
- **Decision:** 本计划不改 handler 层内容定址 / batch 元数据前置；闸门仍在 batch 与 locks。review 形态单测与 `integration_git_lfs`（CL）不得被本计划破坏。
- **Alternatives considered:** 给 PUT 加 token——拒绝（已知 broken pipe 风险，见 protocol.md）。
- **Consequences:** 匿名直连 PUT 仍只能写入已 batch 注册且哈希匹配的字节。
- **Revisit when:** git-lfs 客户端稳定附带 transfer 凭据。
