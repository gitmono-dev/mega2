**模板版本：** v2.1。源码核对日期 2026-09-19；tip `a61ed5f`，crate `0.38.1`。

**计划状态（2026-09-20）：** **实施中**。设计双评已通过（Codex R9 / R11 `VERDICT: PASS`，Claude R11 `VERDICT: PASS`）。发布窗口已落到 `GS-18`（no-release）；下一张是 `GS-27`。其余活动卡仍按单链执行，不得跳卡。

## 文档职责

本文解决「把 `/project` 下的 monorepo 路径内容单向推送到 GitHub 所需的**已定型基础设施**」——配置面、自举凭证与出站 SSH 传输——并用五张 spike 卡冻结尚未定型的设计问题（Q1–Q5 / Q6a / Q6b / Q7 / Q8），再把其余实现移交后续计划。

本文只规划任务，不宣称实现完成。落地时每个任务都必须先刷新源码锚点，再按任务卡验收。

> **成稿背景（R1/R2 评审响应）**：初稿（12 张卡）覆盖完整出站链路。R1（`FAIL`）确认其中 5 项同步语义属未解决设计问题；R2（`FAIL`）进一步确认 `incremental_pack` 硬化同样**未定型**——它需要改动 `RepoHandler` trait 的返回类型（`src/ceres/pack/mod.rs:254` 无流内错误通道），而该 trait 的消费端是**线上 clone/fetch 路径**（`src/ceres/protocol/smart.rs:283`、`src/ceres/protocol/v2.rs:284`）；且「任意缺失的 `have` 返回错误」会破坏 upload-pack 的正常协商语义（服务端只 ACK 自己拥有的 commit，`src/ceres/protocol/smart.rs:275`）。因此本文再次收敛：只保留**不触碰既有协议路径**的基础设施，全部未定型问题进 `GS-09`（spike）。逐条关闭矩阵见「Review log」。

### 适用范围

- `[github_sync]` 配置段：schema、加载注册（含白名单、构造器、重载分类）、启动期 fail-closed 校验
- 自举的 Ed25519 SSH 金钥：生成、跨副本收敛、持有、公钥暴露边界、私钥封闭性
- `src/ceres/github_sync/` 的出站 SSH 连接与 receive-pack 客户端（**新增模块，不改动既有协议路径**）
- `docs/refactoring/github-sync.md` 契约文档（各卡增量写入）
- 五张 spike 卡冻结未定型设计问题（Q1–Q5 / Q6a / Q6b / Q7 / Q8），一张 handoff 卡移交剩余实现

### 非目标

- **`incremental_pack` 硬化与 pack 错误通道设计**：需改动 `RepoHandler` trait 并触及线上 clone/fetch 路径，未定型。由 `GS-18` Q6a / `GS-27` Q6b 冻结、`GS-10` 移交（`DEFER-GS-07`）。
- **出站同步执行链路**（outbox 触发、推送 worker、游标、事件、AI 交接、轮询、命令 API）：语义未冻结，由 `GS-09` Q1–Q5 与 `GS-21` Q7 冻结、`GS-10` 移交（`DEFER-GS-01`）。
- **真实 GitHub 的 live 验收**：本计划只做本地回环验收，不产生任何 GitHub 侧副作用（`DEFER-GS-08`）。
- **GitHub → mega2 入站同步**：永久非目标（`DEFER-GS-02`）。
- **mega2 内建合并**：ADR-GS-04。
- **`main` 以外的分支、tag、产品 GitHub Release**；**产品路径使用 `gh` CLI 或 GitHub REST API**（ADR-GS-03；**不禁止**本仓发布切片用 `gh release create`，见「三问确认」第 2 条）；**`/third-party` 路径**（`DEFER-GS-03`）。

### 成功定义

- 配置 `[github_sync]` 后，启动期即可拒绝全部已知的不可执行组合，且 `enabled=false` 时对既有部署零影响。
- 启动一次即可从日志取得公钥并完成 GitHub 侧准备；私钥在日志、错误文本、`Debug` 三个面均不可见；多副本并发初始化收敛到同一把金钥。
- 可对一个**本地** SSH 服务端完成一次 receive-pack，并在被拒时取得有界的 side-band 诊断。
- 五张 spike 各自给出 go / no-go / 研究未完成三分支判定；`GS-10` 按组合决策表完成移交或替代方向登记。
- 所有非延后任务 `Lifecycle=done` 且 `Acceptance=complete`，review 最终 `PASS`。

1. **使用和测试要什么 key / token？** 见上表。测试 = 层 A（无 GitHub token）。使用/上线 = 层 C（机器用户 + 自举 SSH 公钥 + 钉住的 `ssh_host_key`）。发版 = 层 B（仅 `gh release`）。

3. **计划是否包含刷新 README？** **包含，且分三个文件。** 产品 [`README.md`](../../README.md) 与双语 [`README.zh.md`](../../README.zh.md) 由 **GS-23** 在配置入口补 `[github_sync]` 契约链接（不是产品功能广告）。计划索引 [`docs/plan/README.md`](README.md) 由 **GS-10**（handoff 组合）与 **GS-11**（收口）更新状态行。禁止只改英文不改中文。

## 已决议设计决策

### ADR-GS-01: 只同步 `/project` 下路径的 `main`，映射显式声明

- **Status:** Accepted
- **Context:** 路径 ref 的 commit tree 就是该路径子树（`materialize.rs:262`），故路径与 GitHub 仓库是 1:1 tree 映射。但取叶节点名会碰撞（`/project/a/b/c/foo` 与 `/project/x/y/foo` 都得到 `foo`），且仓库内无 slugifier 或碰撞解析器。
- **Decision:** binding 显式声明 `path` 与 `remote`，不从路径推导；启动校验强制两者各自唯一。只同步 `refs/heads/main`。
- **Alternatives considered:** 路径末段自动推导（拒绝——碰撞后果是两个路径互相覆盖同一仓库，单向推送下为静默数据破坏）；多分支（拒绝——`docs/monorepo.md:14`）。
- **Consequences:** 配置啰嗦；换取冲突在启动期即被拒绝。
- **Revisit when:** monorepo 放开多公开分支时。

### ADR-GS-02: 本计划只支持 trunk 形态，且不新增任何 HTTP 表面

- **Status:** Accepted
- **Context:** `git.push_auth` 一经设置即强制 `push_policy="trunk"`（`src/config/validate.rs:561`–`:565`），而本计划的启动闸要求 `push_auth` 存在，故 trunk 是**推论出的确定边界**，不是待定问题。另一方面，trunk 缺少统一的路由授权层（`http_server.rs:792` 的 `cedar_guard` 不挂载），`push_auth="none"` 时 `authorize_trunk_api_write` 返回匿名（`api_write_auth.rs:34`）。
- **Decision:** 本计划只支持 trunk 形态；**不新增任何 HTTP 路由**。操作接口及其授权设计由 `GS-21` Q7 冻结、`GS-10` 移交。
- **Alternatives considered:** 同时支持 review 形态（拒绝——与 `push_auth` 的强制推论冲突）；在本计划内加命令 API（拒绝——授权设计未定型）。
- **Consequences:** 本计划交付物无任何 HTTP 表面，运行时 OpenAPI 证据为 `N/A`。
- **Revisit when:** trunk 引入统一认证层时。

### ADR-GS-03: 单一凭证——自举的 SSH 金钥，不引入 `gh` 与 REST API

- **Status:** Accepted
- **Context:** SSH 金钥无法认证 GitHub REST API；任何 REST-only 能力都要求第二种凭证，带来第二条轮换路径与第二套审计面。仓库内已有的 GitHub 表面（`mono_api_service.rs:4713`）是 HTTPS 匿名**拉取**，方向与传输均不适用。
- **Decision:** 只用一把 SSH 金钥，启动时自动生成（照 `ensure_server_signing_key`，含 RedLock 跨副本收敛），私钥写入 vault 且不离开进程，公钥经启动日志输出供人工贴入 GitHub 机器账号。不做 branch protection 自动预检。
- **Alternatives considered:** deploy key（不能跨仓库复用）；fine-grained PAT（需 HTTPS 与第二凭证）；`gh auth token`（scope 为该用户全部仓库）。
- **Consequences:** 失去上线前 branch protection 检查，改由首次推送失败承担——因此 GS-08 必须在能力允许时收下 side-band 诊断（ADR-GS-05）。本仓发版仍用发布者 `gh`（层 B），不计入产品凭证。
- **Revisit when:** 需要 REST-only 能力时。

### ADR-GS-04: mega2 不实现任何合并

- **Status:** Accepted
- **Context:** 在 mega2 内做三方合并需要四样东西而均不存在：merge-base 计算（`rg 'merge_base|common_ancestor|three_way' src/` 零命中；`git-internal 0.9.0` 模块只有 `index`/`metadata`/`object`/`pack`/`zlib`）、三方 tree 合并与冲突检测（`CheckType::MergeConflict` 无注册 checker）、2-parent merge commit（`src/ceres/pack/push_chain.rs` 拒绝 merge commit）、从 GitHub fetch（违反单向范围）。
- **Decision:** 非快进时不在 mega2 内合并。处置策略（`abort` / `force`）的判定条件与外部移交协议由 `GS-21` Q7 冻结后随 `GS-10` 实现。
- **Alternatives considered:** `reparent`（产物存不进 mega2）；真三方合并（上述四条阻断）。
- **Consequences:** 本计划不实现任何非快进处置逻辑。
- **Revisit when:** monorepo 模型允许 merge commit 时。

### ADR-GS-05: receive-pack 的能力协商与最低能力集

- **Status:** Accepted
- **Context:** 客户端**只能请求服务端已声明的能力**。取消 branch protection 预检后（ADR-GS-03），失败诊断成为主要信息来源，而详细诊断走 side-band channel 2/3。
- **Decision:** 先解析 advertisement 的能力集；`report-status` 为**最低能力集**——未声明时在**发送任何字节前**拒绝执行；`side-band-64k` 为可选增强，已声明才请求，未声明则降级并在诊断中标注能力缺失。诊断输出有本层显式字节预算（不引用任何已移出本计划的事件字段上限）。
- **Alternatives considered:** 写死 capability（拒绝——违反协议协商规则）；无最低能力集即发送（拒绝——无报告则无法判定结果）。
- **Consequences:** `process_pack_stream`（`third_party.rs:216`）只能作参考：它以发现 `PACK` 为进入条件且返回 pack 数据，与 receive-pack 返回 report-status 的形态不同，不能直接复用。
- **Revisit when:** N/A

### ADR-GS-06: 未定型问题一律进 spike，不进实现卡

- **Status:** Accepted
- **Context:** R1 与 R2 累计确认后拆成 9 个问题域（Q1–Q5 / Q6a / Q6b / Q7 / Q8），由五张 spike 分别冻结。其中 Q6a 尤其关键：`incremental_pack` 的错误传播需要改动 `RepoHandler` trait 的返回类型（`pack/mod.rs:254` 无流内错误通道），而消费端是线上 clone/fetch（`smart.rs:283`、`v2.rs:284`）；且「任意缺失的 `have` 返回错误」会破坏正常协商（`smart.rs:275`）。
- **Decision:** 这 9 个问题域由 `GS-09` / `GS-18` / `GS-27` / `GS-21` / `GS-28` 在时间箱内冻结为 ADR，产出后由 `GS-10` 按 go / no-go / 研究未完成三分支组合处置。本计划不实现任何依赖这些结论的代码，**也不改动任何既有 `src/` 文件的行为**。
- **Alternatives considered:** 在任务卡内补 AC（拒绝——改变的是 trait 契约与状态机，会导致返工）；直接实现并迭代（拒绝——涉及线上协议路径与不可逆远端副作用）。
- **Consequences:** 本计划交付物为纯增量基础设施，对既有功能零行为影响。
- **Revisit when:** N/A

### ADR-GS-07: 凭证分三层，禁止把发布者 `gh` 或 GitHub PAT 做成产品依赖

- **Status:** Accepted
- **Context:** 使用者要求实施前写清「测试 / 使用要什么 key 或 token」。ADR-GS-03 禁止产品路径引入 `gh` / REST，但 ER-08 要求 bump 卡手写 `gh release`。二者若不分层会被读成自相矛盾。

- **Alternatives considered:** 测试也要求 PAT（拒绝——违反 `DEFER-GS-08`）；把 `gh release` 也取消（拒绝——与仓库 ER-08 / 60919 口径冲突）。
- **Consequences:** 开工检查只核层 A；第一张 bump 卡额外核层 B；层 C 只出现在 GS-11 上线清单。
- **Revisit when:** 另开计划引入 REST-only 能力时。

### 本计划引用的模板规则（就地摘录，避免悬空引用）

- **G-03 计数口径**（`plan-template.md:364`）：AC 按「独立 pass/fail 谓词」计，用「且/并且/以及/同时」连接的多个可分别失败的断言按多条计；Verification 按「独立验证门」计，环境准备前缀与其后命令合计为一门。ER-04 的强制门不计入。上限：`implementation`/`migration`/`spike` 为 8，`docs`/`audit`/`handoff` 为 20。
- **Verification 判定口径**（`plan-template.md:478`）：守卫必须区分「零命中」与「命令失败」；仅用于定位符号的 `rg` 须注明「锚点定位用，非判据」；新增 test fn 标 `(new)`；依赖真实服务的用例必须写清前置，把「跳过」当「通过」属幽灵验收。
- **G-01 恢复模式**（`plan-template.md:358`）：`revert` / `forward-only` / `compensating` / `immutable-release` 四选一；`compensating` 必须写出补偿命令与幂等键。
- **C 组禁止重跑 lib**（Cargo 1.98+；覆盖 `plan-template.md` 里把 `--tests` 当成「只跑 `tests/`」的旧口径）：权威命令是**一次** `source .env.test && cargo test --all`（lib + bins + 各 `tests/*.rs` 各一遍）。**禁止** `cargo test --lib` 之后再跑 `cargo test --tests`——`--tests` 现为「所有 `test = true` 的 target」，**包含 lib**。若拆跑：`--lib` 至多一次，集成测试只用 `cargo test --test <name>`（可一次列出全部集成 target），同一时刻本仓只允许一条 `cargo test`。卡内 focused VER 是 ER-04 A 组附加门，不算 C 组重跑。

**本计划的三段公共守卫（`baseline.sh`=`GS-14`，`allowlist.sh`=`GS-22`，`docrefs.sh`=`GS-19`）。三段均已落盘。下列契约在 R2–R5 评审中用隔离夹具复现过正例、越界负例与命令失败三态：**

`scripts/guard/baseline.sh <out>` —— 保存**内容+元数据基线**。每个脏路径记一行 `<kind>|<mode>|<fingerprint>  <path>`：`kind` ∈ `file|symlink|absent|unsupported`；`mode` 为八进制权限位（`symlink`/`absent` 记 `-`）；`fingerprint` 为普通文件的 `sha256`、符号链接的链接目标、`absent` 的字面 `-`。**目录、FIFO、设备等类型记 `unsupported` 并在比对时一律判越界**（拒绝而非静默放行）。仅记内容哈希无法区分「只改执行位」与「替换为指向相同字节的符号链接」，故元数据必须入指纹。

`scripts/guard/allowlist.sh <baseline> <allowed-path>...` —— 比较集合为「**基线路径 ∪ 当前脏路径**」（覆盖已从 status 消失的基线路径）；对不在 allowlist 的路径以上述**完整指纹**与基线比对；重命名对**源路径与目的路径两端**分别判定；`libra status` / `sha256sum` / `stat` / `readlink` / `grep` / `sort` 任一失败即退出 2；allowlist 为空或基线缺失同样退出 2。

`scripts/guard/docrefs.sh <markdown-file>...` —— 逐文件以 `rg -o --no-filename` 提取 `docs/*.md` 引用（`--no-filename` 避免多文件前缀污染），`rg` 退出 >1 或 `sort` 失败即退出 2；悬空引用退出 1。

退出码契约（三段一致）：`0` = 通过，`1` = 判定失败（越界 / 悬空），`2` = 命令或输入错误。**各卡引用 allowlist 守卫时必须传入该卡 `Deliverables` 的确切产物路径，不得传入 `docs` 这类宽目录。**
