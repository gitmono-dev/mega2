## 文档职责

本文解决「monorepo receive-pack 目前每次 push 只允许一个 commit」的限制放开，
目标是交付：**push 侧允许携带一条线性 commit 链（经完整校验），CL 语义与
trunk 不变式完全不动——CL 仍是 `(from_hash → to_hash)` 聚合 diff，CL merge
永远在 `refs/heads/main` 上生成一个全新的单父 commit。**

设计已经过两轮外部评审（Codex / Claude Code，2026-08-26，评审记录见
`target/tmp/codex-review.md` 与 `target/tmp/claude-review.md`，评审对象为
设计简报 `target/tmp/cl-multicommit-brief.md`），结论均为「有条件批准」；
本计划的任务卡即两份评审所提阻塞项的逐条承接。

本文只规划任务，不宣称实现完成。落地时每个任务都必须先刷新源码锚点，再按任务卡验收。

### 适用范围

- receive-pack 接收路径：`src/ceres/pack/monorepo.rs`（含新增 `push_chain` 模块）、
  `src/ceres/pack/mod.rs`、`src/ceres/protocol/smart.rs`。
- 合并检查器：`src/ceres/merge_checker/gpg_signature_checker.rs`。
- CL commit 清单存储与 API：`src/jupiter/storage/cl_storage.rs`、
  `src/api/router/cl_router.rs`、`src/ceres/model/change_list.rs`（响应 DTO）。
- 集成测试 `tests/integration_git_cli.rs` 与文档 `docs/monorepo.md`、
  `docs/errors.md` 的同步。

### 非目标

- **不改 trunk 合并语义**：不允许 main fast-forward 到用户 commit 链，不引入
  merge commit。CL merge 永远 `Commit::from_tree_id(tree, vec![旧main_head], msg)`
  （ADR-MC-01）。
- **不做 Gerrit 式「一 push N CL」**：一次 push 仍只对应一个 CL；按 commit
  拆 CL 是另一个特性，登记为 DEFER-MC-01。
- **不允许 merge commit 入链**（链内双父 commit 一律拒绝）。
- **不动 ImportRepo**：`src/ceres/pack/import_repo.rs:141` 的 `check_entry`
  本就无数量限制（2026-08-26 核对），不在本计划范围。
- 不做 bundle-uri、SHA-256 仓库、`atomic` 多 ref push（walgit 对比分析中的
  其它建议项，各自需要独立计划）。
- UI 改动不在本仓，由 monoui `docs/plan/plan-20260827.md` 承接（DEP-01）。

### 成功定义

- 用户可以 `git push` 一条 N 个 commit 的线性链（N ≤ `MAX_CL_CHAIN_COMMITS`），
  服务端为其创建/更新**一个** CL，CL ref 指向链 tip 且 `ref_commit_hash` 与
  `ref_tree_hash` 同源一致。
- 含 merge commit、断链、tip 与 `cmd.new_id` 不符、超长链、单次 receive-pack
  多条非删除 branch 命令的 push 被明确拒绝，报错文案可操作。
- CL merge 后 main 上恰好新增一个单父 commit（端到端断言）。
- CL 内 commit 链落库 `mega_cl_commits` 并可经 `GET /api/v1/cl/...` 读取，
  运行时 OpenAPI 证据取得。
- GPG 签名检查对链上**每个** commit 生效（不弱化为仅验 tip）。
- 计划完成判据全部满足，评审 PASS。

## 已决议设计决策

实现时若需偏离本节，必须先修改计划并说明原因，不得在代码中静默改语义。

### ADR-MC-01: trunk 不变式——CL merge 永远生成单父新 commit

- **Status:** Accepted（用户决策，2026-08-26）
- **Context:** 放开 push 侧 commit 数量后，trunk 历史粒度由什么决定存在两种可能：快进到用户链 vs 服务端新建单 commit。
- **Decision:** 维持现状——`process_ref_updates` 用合并后的 tree 构造单父新 commit 推进 main；用户 push 的中间 commit 永远不上 main，仅保留在 `refs/cl/<link>` 供审计与 UI 展示。
- **Alternatives considered:** fast-forward 用户链（一 CL N revision）——破坏 Piper「一 CL 一 revision」与评审粒度，拒绝。
- **Consequences:** trunk 线性历史与 commit 数量解耦；本计划 trunk 侧零改动；MC-03 的端到端验收必须断言此不变式。
- **Revisit when:** 若未来引入 Gerrit 式 stacked CL（DEFER-MC-01）。

### ADR-MC-02: CL = `(from_hash, to_hash)` 聚合 diff 不变

- **Status:** Accepted
- **Context:** 评审、diff、merge_checker、构建触发、anchor 重定位全部已是哈希对驱动（2026-08-26 双方评审核实）。
- **Decision:** CL 语义不变。链式 push 后，CL 的 `from_hash` = 链 base 的 parent 基线、`to_hash` = 链 tip；评审者看到的永远是聚合 diff。
- **Alternatives considered:** 按 commit 拆分评审面——属 DEFER-MC-01，不在本计划。
- **Consequences:** 链校验必须保证 base/tip 与 from/to 的一致（MC-03 AC）。
- **Revisit when:** DEFER-MC-01 启动时。

### ADR-MC-03: GPG 对链上每个 commit 验证

- **Status:** Accepted（用户于 2026-08-27 明确确认方案 a：逐 commit 验证，不采用 tip-only 降级）
- **Context:** 今天的隐含保证是"每段合入 trunk 的 diff 都由恰好一个验过签名的 commit 产生"；链式后仅验 tip 会让中间 N-1 个未验证 commit 的内容完整并入 trunk（Claude 评审 B3）。
- **Decision:** `gpg_signature_checker` 从 `to_hash` 沿 parent 链反走到 `from_hash`，逐一验证；任一失败即 checker 失败并指明 commit。遍历史上限 `MAX_CL_CHAIN_COMMITS`。
- **Alternatives considered:** 「tip 签名代表整个 CL」的明示降级——安全语义弱化需单独威胁模型评审，本计划不采纳。
- **Consequences:** MC-02 必须先于 MC-03 落地（单 commit 链下行为与现状完全一致，可独立验收）。遍历史上限的口径以 ADR-MC-07 为准（CL 累计范围 ≤ 250，接收侧已校验，checker 反走天然有界）。
- **Revisit when:** 产品侧正式批准 tip-only 策略并更新威胁模型。

### ADR-MC-04: v1 单次 receive-pack 拒绝多条非删除 branch 命令

- **Status:** Accepted
- **Context:** `Monorepo` 只从第一条 branch 命令初始化 from/to，但持久化阶段遍历全部命令、post-push 只跑一次——多 branch push 今天的行为本就错误（Codex 评审阻塞项 3）。
- **Decision:** v1 遇到一次 receive-pack 中多于一条非删除 branch 命令时报错拒绝，文案引导分次 push；删除命令不受影响。
- **Alternatives considered:** 每条命令一份链一份 CL——状态面与 post-push 管线都要重做，超本计划范围（DEFER-MC-02）。
- **Consequences:** 这是对既有（错误）行为的收紧，客户端影响面为「一次 push 多个分支」的用户；随 MC-06 的 minor 版本发布并在 `docs/monorepo.md` 说明（不得在 MC-03 的 patch 中先行收紧）。
- **Revisit when:** 出现真实的多分支单 push 需求。

### ADR-MC-05: 空 pack / 已知 new_id = 幂等 no-op

- **Status:** Accepted
- **Context:** 对象全部已存在（重复 push、纯 ref 前移场景）时，当前代码静默不写 CL ref、不建 CL（`monorepo.rs:889` 附近，`current_commit` 为空直接返回）。
- **Decision:** 显式定义：pack 中无新 commit 且 `new_id` 指向服务端已知 commit 时，push 成功（report-status ok），CL ref 与 CL 均不变动，report-status 附 `remote:` 提示信息。不为此建 CL。
- **Alternatives considered:** 为此场景补建 CL——from/to 无法从空 pack 推出，语义不明，拒绝。
- **Consequences:** 行为从「静默」变为「静默+提示」，不改变既有的不建 CL 事实；需在 MC-01 实现并在测试断言。**补充（R2）**：no-op 不改 CL 主体，但当 CL 存在而其 `mega_cl_commits` 清单缺失或与当前 `to_hash` 不符时，post-push 管线允许幂等补齐清单（MC-04 AC），这不被视为「建/改 CL」。
- **Revisit when:** 用户反馈该场景需要建 CL。

### ADR-MC-06: 对象 `commit_id` 归属 = 链 tip（语义降级显式化）

- **Status:** Accepted
- **Context:** `save_entry` 把同一 `commit_id` 批量写给整批 tree/blob（`mono_service.rs:104-113`）；链式下精确归属需按每个 commit 的树 diff 反推引入者，成本高。该字段**存在存活读取点**：`item_to_commit_map`（`mono_api_service.rs:1070-1124`）经 `tree_ops.rs:32` 接 `preview_router.rs:50,218-225`（文件浏览的"最后提交"展示；MC01-R1 Claude P1-1 证伪了"无读取点"的原前提）。单 commit/push 强约束下数值恰好正确（tip = 唯一 commit）；多 commit 放开（MC-06）后成为近似值。
- **Decision:** v1 归属写链 tip，语义定义为「该对象在本路径最后一次被某次 push 触及时的链 tip」；在 `docs/monorepo.md` 与代码注释中显式记录非精确值。
- **Alternatives considered:** 树 diff 反推精确归属——读取点虽存在但容忍近似语义（UI 提示性展示），成本不值，登记 DEFER-MC-03。
- **Consequences:** MC-06 放开后"文件最后提交"展示为近似语义（链 tip），属已记录的非精确值；读取点已登记于 MC-06 的 Current evidence；任何新增读取该字段的功能必须先重审本 ADR。
- **Revisit when:** 产品要求精确的"文件最后提交"归属（DEFER-MC-03 重启条件）。

### ADR-MC-07: 链长上限的单一口径 = CL 累计范围（from→to）≤ 250

- **Status:** Accepted
- **Context:** `refs/cl/<link>` 会被广告（`monorepo.rs:92-96` 的 `get_all_refs(path, false)` 不过滤 CL ref；`smart.rs:80-93` 逐一写入广告），因此对既有 open CL 的第二次及以后 push 默认是**增量 push**（pack 只含新增 commit）。`PushChain` 从 tip 反查、遇到 DB 已知 commit 即停，得到的是**本次增量**；而 `update_or_create_cl` 保留冻结的 `from_hash` 只前移 `to_hash`（`code_edit/model.rs:265-266`），MC-02 的 GPG 反走与 MC-04 的全链重建作用在**累计范围**上。若 250 同时充当两种口径，迭代开发同一 CL（如 200+100 两次合规 push）会让累计范围超限，CL 在 GPG 检查处永久失败（2026-08-27 Claude 评审 P0-1）。
- **Decision:** `MAX_CL_CHAIN_COMMITS`（250）只有一种含义：**CL 的 `(from_hash → to_hash)` 累计范围上限**。单次 push 的增量链长上限是其自然子集（增量 ≤ 累计）。对既有 open CL 的更新 push，接收侧除增量校验（MC-03）外，额外做**累计长度校验**：`cl.from_hash → 新 tip` 累计 ≤ 250，超限在 push 阶段 fail-closed 拒绝，文案引导「先合并当前 CL 再开新 CL 或 squash 后重推」。
- **Alternatives considered:** 方案 A（PushChain.base 对既有 CL 一律取 `cl.from_hash`，全程累计口径）——每次 push 的校验成本随 CL 累计长度增长且无必要（已知历史的对象无需重验），拒绝。
- **Consequences:** MC-02 的反走与 MC-04 的重建在接收侧保证下天然有界（≤250）；MC-03 校验器新增累计校验职责；单元测试必须包含「两次 push 累计超限」场景（第一次 200 + 第二次 100 → 第二次被拒）。
- **Revisit when:** 产品需要超长 CL（届时应先引入 stacked CL，DEFER-MC-01）。

### ADR-MC-08: 验签身份路由——每 commit 身份取自其 committer header，服务端身份无回退

- **Status:** Accepted
- **Context:** 现状 `verify_commit_gpg_signature` 的身份完全外部传入且不解析 commit 内容：`verify_cl` 把 `assignee` 固定为 `cl_info.username`（CL 所有者，`src/jupiter/model/cl_dto.rs:26`），`extract_from_commit_content` 只剥离 `gpgsig` 块不返回身份（`gpg_signature_checker.rs:143-171`），公钥按该用户名枚举（`gpg_storage.rs:90-107`）。MC-09 引入服务端合成 commit 后，CL 链会成为「服务端合成 commit + 用户 commit」的混合链（`update_branch` 后再追加 push 是 ADR-MC-07 认可的正常工作流），统一身份假设必然失效（Claude MC09-R1 P0-1）。
- **Decision:** 链上每个 commit 的验签分两步。**① keyring 选择不认 committer email**（用户可控、未验证，仅作展示）：唯一映射来源 = 从签名包解析 issuer fingerprint（pgp 0.20 `Signature::issuer_fingerprint()`，`Cargo.toml:59`），反查 `gpg_key.fingerprint`（unique 列，`src/callisto/gpg_key.rs:18`；格式归一与存储格式 `gpg_storage.rs:47` 一致）定位 key 与所属用户；issuer fingerprint 必须恰好解析出唯一值（hashed subpacket 优先；缺失、多值或与 unhashed 冲突一律 fail-closed，0/1/多三态用例）；反查沿用 `list_user_gpg` 的过期过滤语义（`expires_at` 为空或未过期才纳入候选，`gpg_storage.rs:90-107`）；无命中即 fail-closed，禁止回退到 CL owner/外部 assignee（MC-02 落地）。**② 服务端身份路由**：committer header（name+email）与保留的服务端身份常量比较，判定为服务端身份 → **只**用服务端 keyring 校验（遍历未撤销历史公钥），失败禁止回退到用户 keyring（MC-11 落地）。回退一旦存在，攻击者伪造 committer 即可逃逸，故无回退是硬约束（Codex MC09-R2 P0-1：身份→keyring 映射必须可执行、可信）。
- **Alternatives considered:** 统一用 CL owner 身份（现状）——混合链中服务端 commit 必失败，拒绝；committer email → 平台用户映射——email 用户可控且未验证，且仓内无 email→user 查询通道（`mono_storage.rs:393-433` 的 commit binding 仅用认证 username、不解析 email），拒绝；身份取 author 而非 committer——committer 由服务端在合成时控制、用户 push 时由客户端设置，二者都可接受，选 committer 是因为合成场景下它始终是服务端写入的字段。
- **Consequences:** fingerprint 反查机制与用户 keyring 选择由 MC-02 承接（含「非 CL owner 的已注册用户签名可过、未注册 key 签名 fail-closed」两处行为变化记录）；服务端路由、无回退与负例用例由 MC-11 承接；REL-MC-02 家族原子发布（门控、签名产生、信任域不得分版本拆开）。
- **Revisit when:** 引入更多系统身份（如未来 merge bot）。

### ADR-MC-09: 签名载荷规范化——签名与验签共用完整 commit 字节

- **Status:** Accepted
- **Context:** `mega_commit` 把 `tree`、`parents_id`、`author`、`committer`、`content` 分列存储，且 `content` 只保存 message（`src/callisto/mega_commit.rs:13`、`src/jupiter/utils/converter.rs:187`）；现有 checker 只把 `content`（message）传给验签（`gpg_signature_checker.rs:66`）。而 Git 的 GPG 签名覆盖完整 commit 字节（tree+parents+author+committer+message，剔除 `gpgsig`）。若签/验只在 message 上，签名不绑定 tree/parent/author/committer，`git log --show-signature` 也不成立（Codex MC09-R2 P0-2）。
- **Decision:** 定义唯一的规范化载荷构造函数：完整 commit 字节 = `tree + parents + author + committer + message`（git-internal 的 commit 序列化，剔除 `gpgsig`）。签名端（MC-09）与验签端（MC-02/MC-11）**必须共用同一构造**；持久化侧从 `mega_commit` 分列字段确定性重建同一字节流（用例锁死重建确定性）。
- **Alternatives considered:** 额外存储签名时的原始字节——冗余存储且引入第二事实源，拒绝；只签 message（现状延伸）——签名不绑定内容，安全无意义，拒绝。
- **Consequences:** 验收必须含 `git verify-commit` 等价证据与「篡改 tree/parent/author/committer 任一字段即验签失败」用例；`gpg_status` 结果缓存语义变化，缓存键需 bump（`gpg_status:v1` → `v2`，`commit_ops.rs:59-71`）。
- **Revisit when:** 存储模型改为保存原始 commit 字节。

### 故障恢复矩阵

| 故障点 | 可接受残留 | 恢复动作 | 禁止结果 |

| 链校验中 DB 读失败 | 无 | fail-closed 拒绝 push，客户端重试 | 跳过校验放行 |
