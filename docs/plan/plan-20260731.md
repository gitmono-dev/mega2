# Chat/Notes 退场、Website 用户系统接入与邮件投递迁出计划（2026-07-31）

**模板版本:** v2（成稿符合 `docs/plan/plan-template.md` v2）

## 文档职责

本文解决 monoengine 内与 website 产品面重复的 Campsite 风格 **chat / Notes**，以及浏览器会话仍硬编码 `admin`、Campsite/Tinyship 死配置未落地的问题。目标是：

1. **整栈删除**本仓 chat / Notes（产品能力留在 website `monoengine` 分支）；
2. **完整设计并实现**本仓对 website Better Auth 用户系统的接入（唯一浏览器 IdP）；
3. **保留** Git 引擎所需的 Mono `access_token` / SSH / LFS / Bot 身份路径，以及 `/api/v1/user` 下的 SSH/token/CLA/通知偏好 API（仅更换会话身份来源；**邮件投递偏好语义见 ADR-WA-08**）；
4. **把 website `apps/next-app` 整理进本仓 IT compose**，与现有 `monoengine-it` 数据面 / `monoengine`（profile `app`）一起启动，跑真实 get-session → `/api/v1` 会话集成测试（对标 Mega demo 的「前端 + 后端 + 数据面同栈」形态，但 IdP 是 website next-app，不是 moon/campsite）；
5. **去掉本仓全部邮件（email）投递能力**，改由 website 的邮件通知功能发送；本仓不再持有 SMTP/`lettre`/`[mail]`/email outbox。

本文只规划任务，不宣称实现完成。落地时每个任务都必须先刷新源码锚点，再按任务卡验收。

### 适用范围

- Website 会话接入：`src/api/oauth/`、`OAuthConfig` / `[oauth]`、`SessionUser` / `LoginUser`、CORS、`docs/refactoring/website-auth.md`。
- Chat / Notes 退场：`src/chat/`、`src/api/router/chat_router.rs`、`src/api/notes/`、`src/commands/chat_migrate.rs`、`src/contract/api/chat/`、相关 callisto / jupiter storage、`[chat]` / `ChatConfig`、sidebar 默认项、chat 通知触发器、新 forward-only DROP 迁移。
- **IT compose：** `docker-compose.test.yml` 登记 `website-next`（website `apps/next-app`）、`docs/refactoring/test-infra.md` 服务条目、栈级会话黑盒（`bin/tests/`）、CI 可选 profile 拉起路径。
- **邮件退场与 website 投递：** 删除 `src/mail/`、`EmailChannel`、`[mail]`、admin email-jobs/mail-templates、`email_jobs` / `email_job_attachments`；dispatcher 去 email-primary；产品事件经 website 邮件 API 发送；**同步更新** `docker-compose.test.yml`（去掉 monoengine `MEGA_MAIL__*`；mailpit 改挂 website IT）、`.env.test(.example)`、CI workflow，以及 `docs/refactoring/{website-mail,mail,notification,test-infra,integration,config}.md`、`docs/development.md`、根 `README.md` 邮件章节。
- 文档与发布：`docs/plan/plan-long.md`、上列重构/开发文档、`docs/plan/README.md`、minor 版本发布。

### 非目标

- 不在 monoengine 实现注册 / 登录 / 签发 session cookie（IdP 只在 website）。
- monoengine **不直连读取** website 的 user/session 表（信任路径仍是 get-session HTTP）；不引入 JWT / machine service-account（见 `DEFER-WA-01`）。website-next 容器可有**独立**账户库（IT 默认 SQLite，见 ADR-WA-07）。
- 不把 Mega 的 moon / campsite / MySQL 拉进 `monoengine-it`；本计划的「同栈联调」对象是 **website next-app + monoengine**，仅形态上对标 Mega demo。
- 不移植 website AI chat（`apps/next-app/app/api/chat`）或 `docs-app` 静态文档站；不把 website 仓库的产品 `docker-compose.yml`（nuxt/tanstack profiles）整仓迁入本仓。
- 不完成 PT-12 全量 moon↔`apps/next-app` 功能对照审计（本计划只落地账户信任路径 + 最小会话栈 IT）。
- **不把 CL/issue 事件编排整体迁到 website**（触发仍可由本仓发出）；本计划只迁**邮件投递**。Slack/webhook/in-app 是否保留见 ADR-WA-08（决议：保留 in-app + 可选 slack/webhook，去掉 email 通道）。
- 不删除历史 migration 文件；只追加 DROP。
- 不改 Git smart HTTP / SSH / LFS 的 token 鉴权语义。

### 成功定义

- 无有效 website session cookie 时，`/api/v1` 会话路径不再得到隐式 `admin`；带有效 cookie 时身份与 `GET /api/auth/get-session` 一致；`banned` 用户被拒绝。
- `/api/v1/chat/*`、notes sync、`chat-migrate`、`[chat]` 不存在；新库经 `apply_migrations` 后无 chat/notes 相关表。
- Git Bearer/Basic token 与 SSH 路径回归绿；`LoginUser` JSON 字段为 `website_user_id`。
- **`--profile app --profile web` 可同栈拉起 `monoengine` + `website-next`**；黑盒用例能在 next-app 登录后携带 session cookie 调用 monoengine `/api/v1/user` 并断言身份一致。
- **本仓无 SMTP/`[mail]`/`email_jobs`/admin 邮件表面**；产品事件需发邮件时走 website 邮件 API；进程内不再直接投递邮件。
- **`docker-compose.test.yml` / `.env.test*` / CI / 相关文档**已反映「邮件投递在 website」：monoengine 服务无 `MEGA_MAIL__*`；mailpit 若保留则消费方为 website IT；开发与重构文档不再把本仓 SmtpMailer→Mailpit 当作门禁。
- 全部非延后任务在 REL-01 后 `Lifecycle=done` 且 `Acceptance=complete`（子卡此前仅 `locally-accepted`）；`plan-long.md` / `test-infra.md` / `notification.md` / `mail.md` / `development.md` 已同步；REL-01 minor 已发布。

## 已决议设计决策

实现时若需偏离本节，必须先修改计划并说明原因，不得在代码中静默改语义。

### ADR-WA-01: Website 为唯一浏览器 IdP

- **Status:** Accepted
- **Context:** 账户系统在 website（Better Auth）；本仓 `SessionUser` 为硬编码 admin；Campsite/Tinyship 双后端死代码与「website 唯一 IdP」冲突。
- **Decision:** 浏览器身份只信任 website Better Auth。monoengine **不签发** session cookie。删除 `CampsiteApiStore` 与 `api_store_backend` 双后端。信任路径：读 Cookie → `WebsiteSessionStore::load_user` → `GET {oauth.website_api_base_url}/api/auth/get-session`（转发完整 signed cookie 名=值）→ 映射 `LoginUser`。同时支持 cookie 名 `better-auth.session_token` 与 `__Secure-better-auth.session_token`。无 cookie / 非成功 / 空 body / `user.banned=true` → `AuthRedirect`。**删除**硬编码 admin stub。测试仅允许注入 `FixedUserSessionStore`（或等价 test double），禁止生产旁路开关。
- **Alternatives considered:** 共享 website DB 直接读 session 表（拒绝——耦合与密钥边界）；签发本仓 JWT（拒绝——本计划非目标，见 DEFER-WA-01）；保留 Campsite 后端（拒绝——与架构决议冲突）。
- **Consequences:** `service http` 必须能解析 `website_api_base_url`；跨站 cookie 需同站/父域/反代，文档必须写清。
- **Revisit when:** 需要机机身份或会话缓存时（DEFER-WA-01/02）。

### ADR-WA-02: 身份字段映射

- **Status:** Accepted
- **Context:** website `user` 无 `username` 列；本仓全域以 `username` 为 actor / PK；GPG 使用外部 id 字段。
- **Decision:**

| Website `user` | `LoginUser` | 用途 |
|---|---|---|
| `id` | `website_user_id`（由 `campsite_user_id` 重命名） | GPG 等外部 id |
| `name` | `username` | Git actor、SSH/token/CLA/prefs、Cedar principal |
| `email` | `email` | 通知 settings 首次创建 |
| `image` | `avatar_url` | `/user` 回显 |
| `banned` | （不入结构体） | `true` → 拒绝会话 |
| `role` | （不入结构体） | 管理权仍以 `mono.admin` + Cedar 为准 |

  `name` 为空时用 `email` 的 local-part；仍空则拒绝会话并 `warn`。username 唯一性由 website 展示名治理负责；本仓不新增 users 表。
- **Alternatives considered:** 在 monoengine 维护 username 映射表（拒绝——重复账户系统）；用 email 作 username（拒绝——破坏现有 username 键语义与 Git actor 习惯）。
- **Consequences:** 展示名碰撞可能导致 actor 混同；须在 `website-auth.md` 写明运营约束。
- **Revisit when:** website 引入稳定 unique handle 字段时。

### ADR-WA-03: 双轨认证保留

- **Status:** Accepted
- **Context:** Git CLI 无法携带 Better Auth cookie；现有 `access_token` / SSH 已服务协议路径。
- **Decision:**

| 通道 | 机制 | 本计划 |
|---|---|---|
| `/api/v1` 浏览器 | Cookie → website get-session | 落地 |
| API Bearer | Mono `access_token` → `AccessTokenUser` | 保留 |
| Bot | `bot_` Bearer → `BotIdentity` | 保留 |
| Git HTTP / LFS | Bearer 或 Basic password = token | 保留 |
| SSH | 公钥 → `ssh_keys.username` | 保留 |

  `/api/v1/user` 的 SSH/token/CLA/prefs **保留**；仅 `LoginUser` 来源变为 website session（或显式 `AccessTokenUser` 处保持 token 解析）。
- **Alternatives considered:** 删除 `/user` 设置 API、改由 website 代理（拒绝——SSH/token 是引擎职责）。
- **Consequences:** 文档须明确「浏览器会话 ≠ Git 凭据」；用户仍须在 monoengine 生成 access token 供 Git 使用。
- **Revisit when:** website 代发 mono access token 的产品流程落地时。

### ADR-WA-04: `[oauth]` 配置面

- **Status:** Accepted
- **Context:** PT-10 要求 `[oauth]` 落地或清理；当前仅 CORS 被消费。
- **Decision:** `OAuthConfig` 扩展并真正消费：`allowed_cors_origins`、`website_api_base_url: String`（`service http` 启动路径必填，validate fail-closed）、`session_cookie_names: Vec<String>`（默认上述两个 Better Auth 名）。删除遗留忽略键 `campsite_api_domain`、`tinyship_api_domain`、`api_store_backend`。同步 validate / reload / source / testing 与 `config/config.toml`。
- **Alternatives considered:** 整段删除 `[oauth]`（拒绝——仍需 CORS 与 website 基址）；环境变量硬编码基址（拒绝——破坏 config 单一事实源）。
- **Consequences:** 旧 toml 含遗留键时 validate 必须拒绝或显式迁移说明（本卡选择：**拒绝未知/遗留键**，与现有严格校验风格一致，若当前为 whitelist-ignore 则改为删除键并更新示例）。
- **Revisit when:** 多 website 环境（staging/prod）需 profile 覆盖时（已有 profile 机制，无需改 ADR）。

### ADR-WA-05: Chat / Notes 整栈删除

### ADR-WA-07: website next-app 进入 monoengine-it compose 同栈 IT

- **Status:** Accepted
- **Context:** 会话接入若只有 mock，无法证明真实 Better Auth cookie ↔ monoengine 路径。Mega demo（`mega/docker/demo/docker-compose.demo.yml`）已证明「前端 + 后端 + 数据面」同栈联调价值；monoengine 对应前端是 website `apps/next-app`，不是 moon/campsite。website 自有 compose 与 `monoengine-test-net` 隔离，无法直接做跨服务 IT。
- **Decision:**
  1. 在本仓 [`docker-compose.test.yml`](docker-compose.test.yml) 新增服务 **`website-next`**（`profiles: ["web"]`），build context 为 sibling **`../website`**，dockerfile `apps/next-app/Dockerfile`（与 `orbit` / `monoengine` Dockerfile 的 sibling 约定一致）；加入默认网络 `monoengine-test-net`；宿主映射 `127.0.0.1:17001:7001`。
  2. **不**把 Mega moon/campsite/MySQL 拉进本栈；形态对标 Mega demo，资产对标 website。
  3. website-next 账户库：**IT 默认容器内 SQLite**（Dockerfile 已支持），与 monoengine Postgres **库隔离**（满足「引擎不读 website 表」）；禁止与 `monoengine` 业务库混库。
  4. 栈级联调命令：`docker compose -p monoengine-it -f docker-compose.test.yml --profile app --profile web up -d --wait`（数据面默认 up；`app`+`web` 显式）。`monoengine` 环境注入 `MEGA_OAUTH__WEBSITE_API_BASE_URL=http://website-next:7001`，CORS 含 `http://127.0.0.1:17001`（及文档写明的其它 IT origin）。
  5. 必须按 [`docs/refactoring/test-infra.md`](docs/refactoring/test-infra.md) checklist 登记（healthcheck、零残留、CI 入口、secret 注入）；默认 `up -d --wait` **不**拉起 `web`（避免拖慢无前端需求的数据面循环）。
  6. 最小栈级验收：在 next-app 完成 sign-up/sign-in → 取得 session cookie → 请求 monoengine `/api/v1/user` → 断言 `username` / `website_user_id` 与 get-session 一致（ITW-03）。
- **Alternatives considered:** 仅用 FixedUser mock（拒绝——无法验真实 cookie/CORS）；在 website 仓单独 compose 手动联调（拒绝——不进 `cargo test` / CI 门）；把 next-app 放进默认 up（拒绝——拖慢数据面）；复用 Mega campsite 作 IdP（拒绝——与本计划 website IdP 决议冲突）。
- **Consequences:** ER-01 增补「会话栈 IT 需 sibling `../website`」；CI 可选拉起 `--profile web`；镜像构建耗时需写入性能预算；website 契约漂移由 DEP-01 + ITW-03 捕获。
- **Revisit when:** 需要 Postgres 版 website 账户库、或 E2E 浏览器（Playwright）全链路时（见 DEFER-WA-05）。

### ADR-WA-08: 邮件投递退出 monoengine，由 website 承担

- **Status:** Accepted（2026-07-31 修订：强制 compose + 文档同步）
- **Context:** 本仓 `EmailDispatcher` 以 email 为 primary outbox，扇出 in-app/Slack/webhook；`[mail]`/SMTP/`lettre`/Mailpit IT 自成体系。website 已有 `@libs/email`（Resend/Cloudflare）但**仅**认证验证/重置密码，无产品通知 API。用户要求本仓去掉邮件通知，改用 website 邮件能力；且要求 **docker compose 与相关文档一并更新**，避免代码退场后 IT/手册仍指向本仓 SMTP。
- **Decision:**
  1. **Website 是唯一出站邮件发送方**（含认证事务邮件 + 本仓产品事件触发的通知邮件）。
  2. **monoengine 删除全部邮件投递表面：** `src/mail/`（及孤儿 `src/email/`）、`EmailChannel`、`[mail]`/`MailConfig`、`mail.password` secret 字段、admin `/email-jobs/*` 与 `/mail-templates*`、实体/表 `email_jobs` 与 `email_job_attachments`、依赖 `lettre`（若无其它引用）；**禁止**再以 Mailpit 作为本仓 SMTP 验收门。
  3. **编排仍可留在本仓：** CL/issue/reference 等 triggers 保留；**不再** `enqueue_email_job` / 渲染本仓 mail TOML 模板发信。改为调用 website **内部认证** API（契约由 MN-01 固化），例如 `POST /api/internal/notifications/email`（或等价），body 含 `event_type`、`to`、`locale`、模板变量或预渲染字段；鉴权用共享 bearer（配置项，非浏览器 cookie）。Website 用 `@libs/email` 发送并扩展产品模板。
  4. **Dispatcher 去 email-primary：** `NotificationService` 启动**不得**依赖 `[mail]`；若保留 in-app/Slack/webhook，primary 改为 `in_app`（或「无 primary、各通道独立」——开工选一并写进 MN-02；默认 **primary = in_app**）。用户 prefs 中 `delivery_mode=email` 改为「请求 website 发信」或迁移为 `in_app`（MN-02 写清兼容窗口；默认：`email` 模式映射为「调用 website + 仍写 in-app」）。
  5. **Chat 邮件**随 RM-03 删除，不迁到 website（chat 产品面已退场）。
  6. **禁止**本仓再直连 Resend/Cloudflare/SMTP（避免双份凭据）。
  7. **Compose + 环境 + 文档强制同步（与代码同里程碑，不得后补）：**
     1. **`docker-compose.test.yml`：** 删除 `monoengine` 服务上全部 `MEGA_MAIL__*`（含 `MEGA_MAIL__ENABLED`）；`monoengine` **不得** `depends_on: mailpit`。
     2. **`mailpit` 去留：** 默认**保留**服务（便于 website-next 认证/产品邮件在 IT 中 SMTP 捕获）；在 `test-infra.md` 明确 **消费方 = website（或 profile `web`），不是 monoengine**。若 DEP-06/website IT 确认不需要 SMTP 捕获，可改为 `profiles: ["mail"]` 或删除——须在 MN-06 写清并改文档/CI；**禁止**留下「本仓 SmtpMailer→Mailpit」的默认说明。
     3. **`website-next`（ITW）：** 需要发信验收时，注入 SMTP→`mailpit:1025`（或 website 既有测试 provider env）；注入 monoengine→website 邮件 API 所需的内部 bearer / base URL 与 `monoengine` 侧 `notification.website_mail_*`（或 MN-01 定名）对称。
     4. **`.env.test` / `.env.test.example`：** `MAILPIT_*` 若保留，注释改为「website IT 捕获」；删除「本仓 `[mail]` / `mail.password` seed」步骤；新增 website mail client / bearer 的 IT 占位（无真实生产 secret）。
     5. **CI（`.github/workflows/`）：** 去掉本仓 SMTP/`mail.password` 强制门；mailpit 启动仅在 website 邮件 IT 或显式 profile 需要时保留，并在 workflow 注释写明用途。
     6. **文档清单（MN-06 主改，DOC-01 复核）：** `docs/refactoring/website-mail.md`、`mail.md`（废止）、`notification.md`、`config.md`、`test-infra.md`、`integration.md`、`docs/development.md`、根 `README.md` 的 `[mail]`/SMTP 章节、`plan-long.md` PT-09；OpenAPI/运维若仍写 email-jobs 一并清。
- **Alternatives considered:** 仅把 `mail.provider=http` 指到 website 而保留 `email_jobs`（拒绝——用户要求去掉本仓邮件通知/outbox）；把整个 notification 迁 website（拒绝——CL/issue 事件源在本仓，范围过大）；裸删 EmailChannel 不改 primary（拒绝——拖死扇出）；只改 Rust 代码、compose/文档后补（拒绝——用户明确要求同步更新）。
- **Consequences:** 依赖 DEP-06（website API 可用）才能绿 MN-05/MN-06；PT-09 邮件对齐改为「投递在 website」；minor breaking 见 ADR-WA-06；MN-06 写集含 compose/env/docs，粒度仍为 M（与测试改写同卡，避免文档漂移）。
- **Revisit when:** website 侧出现完整用户通知中心后，可再评估是否下沉 triggers（DEFER-WA-07）；mailpit 是否从默认 up 集挪到 `profiles: ["mail"]`（运维成本权衡）。

## 全局工程约束

以下约束对本文所有任务生效。任务条目不再逐条重复，违反任一项即视为任务未完成。

- **GC-01 现状核实前置:** 每个任务开工前重新核对计划、相关开发文档、当前代码和测试。如果已实现，则任务改为补测试、补文档、更新状态或关闭，不重复实现。

- **GC-06 测试覆盖:** 新增 / 改动的 storage / migration / 会话解析必须有 focused 测试；删除表面必须有零命中守卫。

- **GC-09 并发与资源生命周期:** website HTTP 客户端须有超时；测试注入 store 不得泄漏跨用例全局状态。
- **GC-10 性能预算:** 本计划接受每请求 get-session 外呼；禁止在 handler 内无界重试。
- **GC-11 生产 panic 禁止:** 生产路径不得新增裸 `unwrap()` / `expect()` / `panic!()`；`TinyshipApiStore::new` 现有 `expect` 在迁到 `WebsiteSessionStore` 时必须改为可返回错误或启动期 `MegaResult`。
- **GC-12 精确提交:** 只 `libra add <相关路径>`；本仓无 `.git`。
