# 集成测试基建扩展与统一计划（2026-07-27）

## 文档职责

本文解决 `plan-long.md` PT-01（集成测试基建扩展与统一）的落地，目标是：统一测试双层规范与 docker-compose 拓扑扩展机制，交付真实 Git CLI smoke 最小矩阵（HTTP 通道 clone/push）作为示范负载，落地热加载黑盒与并发 dispatcher 端到端投递基线用例，并收口 `docs/refactoring/integration.md` 的 P2 清单。

本文只规划任务，不宣称实现完成。落地时每个任务都必须先刷新源码锚点，再按任务卡验收。

### 适用范围

- `docker-compose.test.yml` 测试栈拓扑扩展机制与首个扩展服务（Git CLI runner）。
- `bin/tests/` 黑盒测试分层规范与新文件 `bin/tests/integration_git_cli.rs`（HTTP clone/push 最小矩阵）、热加载黑盒用例、并发 dispatcher 端到端投递基线用例。
- `.github/workflows/` CI 接入与 `docs/refactoring/integration.md` P2 清单/覆盖矩阵收口。
- `docs/plan/plan-long.md` PT-01 状态同步。

### 非目标

- 不追求覆盖率数字；本计划只为后续 PT 提供验收承载。
- 不重写既有测试（`integration_vault.rs`、notification 模块集成测试保持不动，仅规范引用方式）。
- Git 协议专项矩阵的完整用例面（SSH/LFS 通道、故障路径、Mega `tests/` 夹具审计移植）属 PT-04，见 DEFER-IT-01/02。
- orion-server、fake webhook receiver 等后续 PT 的拓扑接入只定义规范，不预先实现，见 DEFER-IT-04。
- 真多进程黑盒 claim 竞争矩阵属 PT-09，见 DEFER-IT-03。

### 成功定义

- 新服务接入 docker-compose 测试栈有书面标准流程，并以 Git CLI runner 为首个示范落地。
- 真实 `git` 客户端对测试进程启动的 monoengine HTTP 服务完成 clone/push 正路径，CI 绿。
- 热加载黑盒用例与并发 dispatcher 端到端投递基线用例进入 CI 可运行形态。
- integration.md P2 清单每一项都有"已落地（证据）/ 关闭（理由）/ 延后（承接编号）"结论。
- 全部任务三门验收通过且 review 闭环后，PT-01 在 `plan-long.md` 标记"已实现"（完成判据逐条对照）。

## 已决议设计决策

实现时若需偏离本节，必须先修改计划并说明原因，不得在代码中静默改语义。

### ADR-IT-01: Git CLI 由 docker-compose 固定镜像的 runner 容器提供

- **Status:** Accepted
- **Context:** 真实 Git CLI 矩阵需要版本确定的 `git` 客户端。CI runner 自带 git 版本随镜像漂移，破坏"固定 tag"纪律；直接安装又引入 CI 环境差异。
- **Decision:** 在 `docker-compose.test.yml` 增加 `git-cli` 服务，使用固定 tag 的轻量镜像（含 git 客户端），`network_mode: host`（Linux CI 可直连测试进程在 `127.0.0.1` 高位端口启动的 monoengine 服务），工作卷挂载到测试临时目录。
- **Alternatives considered:** 宿主机 git（版本漂移，拒绝）；testcontainers.rs（新依赖，违反 integration.md "不要为了集成测试新增不必要依赖"，拒绝）；GitHub Actions services 语法（与本地 `docker compose` 路径分裂，拒绝）。
- **Consequences:** 本地非 Linux 环境（macOS Docker Desktop 无 host 网络）需降级为宿主机 git 并在用例输出中记录 `git --version`；镜像 tag 升级是显式 PR 动作。
- **Revisit when:** PT-04 需要 SSH 通道（sshd 拓扑）或矩阵规模显著扩大时。

### ADR-IT-02: Git CLI 黑盒用例放 `bin/tests/integration_git_cli.rs`，编排只用 std + 现有依赖

- **Status:** Accepted
- **Context:** 黑盒进程测试的既有落点是 `bin/tests/`（`integration_vault.rs`），编排方式为 `std::process::Command` + `CARGO_BIN_EXE_monoengine`。
- **Decision:** 新建 `bin/tests/integration_git_cli.rs`，复用 `integration_vault.rs` 的 `VaultCliEnv`/`isolated_command` 模式（必要时抽 `bin/tests/common/` 共享模块），由测试进程启动 `service http`（高位端口、临时 `base_dir`/`cache_dir`、隔离 DB schema），调用 git-cli 容器或宿主机 git 执行 clone/push。
- **Alternatives considered:** 写入 `integration_vault.rs`（文件职责膨胀，拒绝）；引入 assert_cmd/pexpect 类依赖（非必要，拒绝）。
- **Consequences:** 共享辅助抽取时不得改变 `integration_vault.rs` 既有用例行为；新文件用例默认 `--test-threads=1` 串行（端口与 DB 资源）。
- **Revisit when:** PT-04 扩展 SSH/LFS 通道时重审编排抽象是否仍够用。

### ADR-IT-03: 多实例 outbox 竞争用例以端到端并发 dispatcher 投递形态落地

- **Status:** Accepted
- **Context:** storage 层并发 claim 已有覆盖（`concurrent_claim_only_allows_one_sender`、独立连接变体、stale 恢复，`notification_storage.rs:1254/1313/1372`）；未覆盖的是两个完整 dispatcher 实例对同一 DB 的端到端投递竞争（重复发送风险）。真多进程黑盒成本高。
- **Decision:** 在模块集成测试层对同一测试 DB 运行两个完整 dispatcher 实例，并发执行 outbox 投递循环（真实 Mailpit），断言每封邮件恰好投递一次（无重复发送、无丢失）。
- **Alternatives considered:** 真多进程黑盒（留给 PT-09，DEFER-IT-03）；重复 storage 层 claim 测试（已有覆盖，无增量证据，拒绝）。
- **Consequences:** 若用例暴露 dispatcher 层重复发送缺陷，缺陷修复属于本任务范围并触发版本 patch +1；用例形态不覆盖进程级崩溃窗口。
- **Revisit when:** PT-09 落地真多实例部署时。

## 全局工程约束

以下约束对本文所有任务生效。任务条目不再逐条重复，违反任一项即视为任务未完成。

- **GC-01 现状核实前置:** 每个任务开工前重新核对计划、相关开发文档、当前代码和测试。如果已实现，则任务改为补测试、补文档、更新状态或关闭，不重复实现。
- **GC-02 单一事实源:** entity 定义、配置解析、API schema、权限策略、错误码和共享 helper 必须有单一事实源。禁止 CLI handler、HTTP handler、migration 和测试 fixture 各自复制等价逻辑。
- **GC-03 Mega 目标项目与 monoengine 扩展边界:** 直接从 Mega 移植的代码表面必须标注来源和差异；monoengine-only 表面必须说明替代方案、用户影响和机器接口。
- **GC-04 输出与错误契约:** 用户可见错误使用 `MegaError` 稳定变体并同步 `docs/errors.md`。HTTP 状态码、JSON 响应、CLI 退出码和人读输出必须分别验收。
- **GC-05 文档同步:** 命令、配置、HTTP API 或公开行为变化必须同步对应 `docs/` 下文档和 OpenAPI schema。
- **GC-06 测试覆盖:** 新增 entity / storage / migration 必须附带 `#[cfg(test)] mod tests`，使用 `test_db_connection` + `apply_migrations` 集成测试。新增 CLI 子命令必须附解析测试。
- **GC-07 安全默认值:** 未满足认证、授权（Cedar）、路径归属、schema 版本、对象闭包或 secret redaction 前置时默认 fail-closed。任何 fail-open 必须有显式用户选择、日志和测试。
- **GC-08 原子性与恢复:** 修改 DB 事务、redis 状态、对象存储、配置、vault secret 或发布状态时，必须定义事务边界、幂等键、崩溃窗口和回滚/前滚策略。
- **GC-09 并发与资源生命周期:** DB 连接池、redis 连接、文件句柄、异步任务队列和临时目录必须有释放/恢复语义；测试不得依赖未隔离的全局状态。
- **GC-10 性能预算:** HTTP 热路径、DB 查询、对象存储读写、Git 协议操作和后台任务不得引入无界扫描、无界内存或 N+1 DB/网络调用。需要时写出数据规模和断言。
- **GC-11 生产 panic 禁止:** 生产路径不得新增裸 `unwrap()`、`expect()`、`panic!()`；必须用 `MegaResult`、`anyhow::Context` 或领域错误返回可操作信息。
- **GC-12 精确提交:** 提交前只 `libra add <相关路径>`（本仓由 libra 管理，无 `.git`，`git add` 不可用），不得使用 `commit -a`。发现无关脏状态时保留并报告，不得清理、重置或混入提交。

## 执行检查必备需求（强制）

任一要求未满足，对应任务不得标记完成。

1. **开工前安全检查:** 必须使用 libra 运行 `libra status --short`，确认当前分支、工作区脏状态和目标文件是否已有无关改动。若目标文件已有未确认用户改动，先报告并避免覆盖。
2. **先核对后实现:** 刷新本任务相关源码锚点、文档锚点、测试 target 和外部参照 revision，再决定实现、补测、补文档、关闭或降级。
3. **每个任务三门验收:** 至少通过 `cargo +nightly fmt --all --check`、`cargo clippy --all-targets --all-features -- -D warnings`、任务卡指定的 `source .env.test && cargo test ...`。不能用泛泛的 `cargo test` 替代指定用例；指定用例之外还必须通过全量门禁 `source .env.test && cargo test --all`（`AGENTS.md` 强制），指定用例与全量门禁不可互相替代。
4. **代码 review 闭环:** 实现和本地验收完成后进行代码 review；review 问题修复后重跑相关验收，直到 review 明确通过。
5. **文档与兼容同步:** 涉及公开行为的任务必须同步用户文档、开发文档、OpenAPI schema、配置示例、错误码和测试。
6. **构建不变量:** `cargo build` 和 `cargo build --tests` 必须 0 错误 0 警告，且不得新增 crate 级 `#[allow(...)]`。
7. **版本与发布:** 本计划主体是测试基建，无用户可见代码改动，版本号动作默认为 `N/A`；例外：IT-06 若暴露并修复投递缺陷、或任何任务顺带修改生产代码，该任务按开工时实际版本号 patch +1 同步两个 `Cargo.toml` 并记录构建证据。
8. **push 失败策略:** 非 fast-forward 需要 pull/merge 后重新验收再推；认证、权限、网络或服务端失败不 blind retry，记录原因，待下一次修复/发布窗口处理。
9. **内部服务错误:** Redis、Postgres、对象存储、SMTP、AI provider 等暂时性错误不得直接把任务宣告完成。记录错误并在同一步重试；确定性代码或配置错误转为当前任务修复项。
10. **证据卫生:** 验收证据不得保存 secret、API key、token、PII、未脱敏 transcript、绝对私有路径或原始 tool payload。需要留存时只写 sanitized summary。

| IT-06 暴露投递缺陷 | 缺陷用例失败 | 转当前任务修复项（缺陷修复 + 回归），不得跳过或 `#[ignore]` | 删除/弱化用例以通过验收 |
| CI 凭据/token 失效 | job 失败 | 记录原因，不 blind retry；待下一次修复窗口（执行检查第 8 条） | 在日志中打印 secret 排查 |
